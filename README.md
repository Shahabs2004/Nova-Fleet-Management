| بخش | توانمندی |
|---|---|
| داشبورد | آمار زنده مأموریت‌ها، ناوگان آماده/درگیر، روند درخواست‌ها و پیامک‌ها |
| مأموریت‌ها | ثبت، بررسی، تأیید با تخصیص راننده/خودرو، رد، تمدید، خاتمه زودهنگام، لغو، انصراف و تغییرات میانی مسیر |
| کنترل تداخل | سنجش راننده و خودرو بر پایه **زمان برنامه‌ریزی‌شده** با حداقل فاصله (Gap) قابل تنظیم؛ با رسیدن پایان برنامه، منابع آزاد می‌شوند |
| تفکیک مأموریت | شکستن یک مأموریت به چند بخش با دلایل قابل تنظیم (خرابی خودرو، تعویض راننده، …) |
| کیلومترشمار | ثبت شروع/پایان و محاسبه مسافت پیموده‌شده |
| حکم مأموریت | تولید PDF راست‌به‌چپ A4 با سربرگ، فیلدها، کادر امضا و پاورقم؛ قابل چاپ و بایگانی |
| رانندگان | پرونده کامل، وضعیت استخدام، خودروی پیش‌فرض، بایگانی با دلیل |
| خودروها | وضعیت فنی (سرویس/تعمیرگاه/خارج از سرویس)، بایگانی، و آمادگی ذاتی جدا از درگیری زمانی |
| مقاصد | چرخه تأیید/رد/غیرفعال‌سازی برای جلوگیری از ورود مبدأ و مقصد تکراری یا نامعتبر |
| پیامک | صف با تلاش مجدد و ردیابی وضعیت تحویل، قالب‌های قابل ویرایش برای هر رویداد، درگاه payamSMS (WSDL) یا شبیه‌سازی |
| نظیر به نظیر | اعلان‌های درون‌برنامه‌ای خوانده‌نشده |
| امنیت | نشست‌های فعال با پایان اجباری، دفتر رویداد (Audit Trail) قابل فیلتر، کاربران، نقش‌ها و مجوزهای دانه‌درشت |
| گزارش‌ها | گزارش‌های پارامتری با خروجی Excel و PDF |
| خط زمانی | یک ردیف برای هر راننده، با نوار پیوسته مأموریت‌ها از ساعت شروع تا ساعت پایان؛ زوم از **یک ساعت** تا **دو ماه**، برچسب ماه/روز/ساعت، خط «اکنون»، و کلیک روی هر نوار برای دیدن و ویرایش همان‌جا |
| پیکربندی | نام/لوگوی سازمان، قواعد مأموریت، سیاست نشست و قالب حکم، از داخل خود سامانه |
| اتصال سرویس‌ها | تب «تنظیمات ← اتصال سرویس‌ها» برای دیتابیس، دامنه، درگاه پیامک و عملیات — با تست زنده هر اتصال: `ping` و مهاجرت‌های معوق پایگاه، bind + جست‌وجوی نمونه دامنه با شمارش نتیجه، `Balance` درگاه و ثبت پیامک آزمایشی در صف |

## پشته‌فناوری

- **بک‌اند:** ASP.NET Core 10 (Minimal API)، EF Core 10، SQL Server
- **معماری:** Clean Architecture چهارلایه (Domain ← Application ← Infrastructure ← Api)
- **احراز هویت:** کوکی `nf_session` + هدر CSRF + هش رمز PBKDF2-SHA256 + مجوزهای مبتنی بر کد
- **فرانت‌اند:** React 19، TypeScript، Vite 8، Tailwind CSS 4، React Query، React Router 7، Recharts
- **خروجی:** QuestPDF ( سند حکم و گزارش PDF )، ClosedXML ( Excel )
- **پشت‌زمینه:** `MissionLifecycleWorker` (انتقال خودکار وضعیت و آزادسازی منابع) و `SmsQueueWorker` (ارسال و بررسی تحویل)
- **طراحی:** تم «Emerald Premium» — سبز زمردی `#0F766E`، طلایی `#C8A44A`، سطح `#F6F8F7`، فونت وزیرمتن، کاملاً RTL

## ساختارمخزن

```
NovaFleet.sln
src/
  NovaFleet.Domain/            موجودیت‌ها، حالت‌ها و قواعد کسب‌وکار
  NovaFleet.Application/       سرویس‌ها، DTOها، مجوزها و انتزاع‌ها
  NovaFleet.Infrastructure/    EF Core، LDAP، درگاه پیامک، PDF، احراز هویت
  NovaFleet.Api/               Program.cs، endpointها، میدل‌ور، Workerها
web/                           فرانت‌اند React (صفحه‌ها، کامپوننت‌ها، استایل Emerald)
scripts/provision-db.sql       ساخت پایگاه داده، لاگین برنامه و نقش‌دسترسی‌ها
scripts/seed-demo.sql          داده نمایشی (راننده، خودرو، مأموریت، پیامک)
tests/                         پروژه‌های NovaFleet.UnitTests و NovaFleet.IntegrationTests
docs/screenshots/              تصویرهای همین README
```

> پوشه `src/NovaFleet.Api/wwwroot/` میزبان خروجی build فرانت‌اند در حالت یکپارچه است؛ در محیط توسعه لازم نیست چیزی داخل آن باشد.

## پیش‌نیازها

| ابزار | نسخه مورد نیاز | بررسی با |
|---|---|---|
| .NET SDK | ۱۰.۰.۴xx (کلید `global.json` روی `10.0.403` با `rollForward: latestFeature` قفل شده) | `dotnet --version` |
| Node.js | ۲۰ یا بالاتر (توسعه روی ۲۴ انجام شده) | `node -v` |
| SQL Server | ۲۰۱۹ یا بالاتر، با احراز هویت ترکیبی (لاگین `sa`) | `SELECT @@VERSION` |
| sqlcmd | هر نسخه با پشتیبانی `-i` و `-v` | `sqlcmd -?` |
| فونت Tahoma | فقط برای خروجی PDF فارسی | مسیر `C:\Windows\Fonts\tahoma.ttf` |

> **محدودیت SQL Server 2019:** این نسخه `AT TIME ZONE 'Asia/Tehran'` را نمی‌شناسد، بنابراین همه محاسبات وقت تهران (`+۳:۳۰`) در EF Core با `DATEADD(MINUTE, ±210, …)` ترجمه می‌شوند. روی SQL Server 2022 به بعد هم همین کوئری‌ها درست کار می‌کنند و تغییری لازم نیست.

## راه‌اندازی‌کامل‌پس‌از‌دانلود

هشت گام، از clone تا اولین ورود. کدها برای Git Bash روی ویندوز نوشته شده‌اند؛ تفاوت معادل PowerShell یا لینوکس فقط در مسیرها و جداکننده‌های فایل env است.

**۱) دریافت مخزن و پیش‌خوانی build**

```bash
git clone https://github.com/Shahabs2004/Nova-Fleet-Management.git
cd Nova-Fleet-Management
dotnet build          # باید بدون warning و error تمام شود
cd web && npm install && cd ..
```

`dotnet build` راه‌حل چهارلایه و دو پروژه تست را می‌سازد. `npm install` فقط برای محیط توسعه لازم است؛ در حالت production خروجی از `npm run build` به `wwwroot` کپی می‌شود.

**۲) ساخت پوشه اسرار (بیرون از مخزن)**

```bash
mkdir -p "$HOME/.novafleet"
```

سه فایل env در این پوشه می‌نشیند: `db.env` (برای اسکریپت راه‌اندازی)، `app.env` (برای اجرای اپلیکیشن) و `ldap.env` (اختیاری، فقط تست دستی دامنه). شکل هر سه در بخش [راه‌اندازی پایگاه داده](#راه‌اندازی‌پایگاه‌داده) آمده است. **هیچ‌کدام داخل مخزن نمی‌آید و هیچ رمزی در فایل‌های پروژه وجود ندارد.**

اپ به‌محض بالا آمدن دو چیز دیگر در همان پوشه می‌سازد (نیازی به ساخت دستی ندارند، ولی باید در پشتیبان‌گیری باشند):

| مسیر | نقش |
|---|---|
| `~/.novafleet/bootstrap.json` | رشته اتصال write-only؛ گام دیتابیس Setup و تب «اتصال سرویس‌ها» همین‌جا می‌نویسند |
| `~/.novafleet/keys/*.xml` | حلقه کلید Data Protection که رمزهای داخل دیتابیس با آن رمزنگاری/رمزگشایی می‌شوند |

**۳) ساخت پایگاه داده، لاگین برنامه و جدول‌ها**

```bash
set -a; . "$HOME/.novafleet/db.env"; set +a
sqlcmd -S "$SQL_HOST" -U "$SA_USER" -P "$SA_PASSWORD" \
  -i scripts/provision-db.sql \
  -v DbName="$DB_NAME" -v AppLogin="$APP_LOGIN" -v AppPassword="$APP_PASSWORD"
```

اسکریپت، پایگاه `NovaFleetDb`، لاگین سطح‌سرور برای برنامه (`CHECK_POLICY = ON`) و کاربر همان دیتابیس را می‌سازد و آن را عضو `db_owner` **همان پایگاه** می‌کند؛ این سطح لازم است چون مهاجرت EF Core در استارت‌اپ جدول می‌سازد. لاگین به هیچ پایگاه یا سرور دیگری دسترسی ندارد و اجرای دوباره اسکریپت بی‌خطر است. جدول‌ها را هنوز چیزی نساخته‌اید؛ مهاجرت EF Core در گام بعد خودکار اعمال می‌شود.

**۴) اجرای API**

```bash
set -a; . "$HOME/.novafleet/app.env"; set +a
ASPNETCORE_URLS=http://localhost:5192 dotnet run --project src/NovaFleet.Api
```

در استارت‌اپ، `DatabaseInitializer` دو کار می‌کند: `db.Database.MigrateAsync()` (ساخت همه جدول‌ها) و بذرگذاری idempotent پنج نقش، چهار دلیل تفکیک و نه قالب پیامک. اگر رشته اتصال تنظیم نشده باشد، اپ با پیام «رشته اتصال تنظیم نشده است» بالا نمی‌آید.

**۵) اجرای فرانت‌اند (ترمینال دوم)**

```bash
cd web
npm run dev
# http://localhost:5173
```

Vite مسیر `/api` را به `http://localhost:5192` پروکسی می‌کند، پس در توسعه نیازی به تنظیم CORS نیست.

**۶) ویزارد راه‌اندازی اولیه در `/setup`**

در اولین بازدید، صفحه ورود خودکار به `/setup` می‌رود. ویزارد شش گام دارد — پایگاه داده → دامنه → پیامک → سازمان و مدیر → قواعد و ظاهر → تأیید — و جزئیات هر گام در بخش [ویزارد راه‌اندازی اولیه](#ویزارد‌راه‌اندازی‌اولیه-setup) آمده:

```
http://localhost:5173/setup
```

اگر پایگاه داده هنوز ساخته نشده، همان گام ۱ آن را می‌سازد و مهاجرت را اعمال می‌کند؛ در غیر این صورت اتصال فعلی را از `GET /api/setup/database` می‌خواند و فیلدها را پیش‌پُر می‌کند. در گام ۴ یک مدیر سامانه با رمز (حداقل ۸ نویسه) ساخته می‌شود.

این ویزارد **یک‌بارمصرف** است: اگر حتی یک کاربر در پایگاه وجود داشته باشد، هر فراخوانی `/api/setup/*` (از جمله گام دیتابیس) با خطای ۴۰۹ «راه‌اندازی اولیه قبلاً انجام شده است.» پاسخ می‌دهد و صفحه ورود دیگر به آنجا ریدیرکت نمی‌کند. مدیری که اینجا ساخته می‌شود ستون `IsLocalAdmin = 1` می‌گیرد، یعنی مجوز `*` (همه ۴۲ کد) به‌علاوه نقش `Administrator` — تنها حسابی که تب «تنظیمات» و بخش کامل امنیت را می‌بیند.

> تنظیمات دامنه و پیامک را می‌توانید در همین گام‌ها بدهید؛ پس از نصب، همان فرم‌ها در تب «تنظیمات ← اتصال سرویس‌ها» (با مجوز `settings.connections.manage`) و بقیه در تب «تنظیمات» قابل ویرایش‌اند. جزئیات اتصال سرویس‌ها با تست زنده در برنامه است و فعلاً مسیرهای API‌شان آماده است.

**۷) داده نمایشی (اختیاری، ولی برای دیدن برنامه توصیه می‌شود)**

بدون داده، داشبورد و تایم‌لاین خالی‌اند. بخش [داده نمونه و حساب‌های نمایشی](#داده‌نمونه‌و‌حساب‌های‌نمایشی) روش کاملش را با رمز هش‌شده و پارامتر `CleanMode` توضیح می‌دهد.

**۸) ورود**

با همان مدیری که در `/setup` ساختید وارد شوید (تب «ورود محلی»). اگر داده نمونه را بارگذاری کرده‌اید، هش حساب‌های `demo.*` را هم دارید. از اینجا:

| اگر می‌خواهید… | بروید به | نیازمند |
|---|---|---|
| مأموریت ثبت و تا تأیید پیش ببرید | `/missions` → «مأموریت جدید» | `missions.create`، `missions.approve` |
| تایم‌لاین را با زوم تست کنید | `/timeline` | `missions.view` |
| گزارش بگیرید و Excel/PDF دانلود کنید | `/reports` | `reports.view` |
| نقش و مجوز و نشست بسازید | `/security` | `security.audit.view`، `security.sessions.view` |
| قواعد مأموریت، لوگو و قالب حکم را عوض کنید | `/settings` | `settings.system.manage` (سمت UI و سرور)؛ اتصال سرویس‌ها جدا با `settings.connections.manage` |

## راه‌اندازی‌پایگاه‌داده

> **اصل مهم:** هیچ رمز عبوری داخل مخزن نگهداری نمی‌شود. اطلاعات اتصال فقط در فایل‌های env بیرون از مخزن (`C:\Users\<you>\.novafleet\`) و از طریق متغیرهای محیطی وارد فرآیند می‌شوند. `scripts/provision-db.sql` تنها از متغیرهای sqlcmd استفاده می‌کند و به‌تنهایی بی‌خطر است.

**۱) فایل‌های env** (یک‌بار، دستی):

`~/.novafleet/db.env` — فقط برای اسکریپت راه‌اندازی:

```
SA_USER=sa
SA_PASSWORD=<رمز sa>
SQL_HOST=<IP یا نام سرور>
DB_NAME=NovaFleetDb
APP_LOGIN=novafleet_app
APP_PASSWORD=<رمز لاگین برنامه>
```

`~/.novafleet/app.env` — برای اجرای اپلیکیشن. فقط رشته اتصال و تنظیمات فرآیند؛ تنظیمات دامنه و پیامک در پایگاه داده نگه داشته می‌شوند و دیگر اینجا نمی‌آیند:

```
SQL_HOST=<IP یا نام سرور>
DB_NAME=NovaFleetDb
APP_LOGIN=novafleet_app
APP_PASSWORD=<رمز لاگین برنامه>
```

`~/.novafleet/ldap.env` — فقط برای تست دستی مسیر دامنه؛ هیچ‌گاه به مخزن یا لاگ راه ندارد:

```
LDAP_HOST=…
LDAP_PORT=…
LDAP_SSL=…
LDAP_DOMAIN=…
LDAP_USERNAME=…
LDAP_PASSWORD=…
```

**۲) ساخت پایگاه داده:**

```bash
set -a; . "$HOME/.novafleet/db.env"; set +a
sqlcmd -S "$SQL_HOST" -U "$SA_USER" -P "$SA_PASSWORD" \
  -i scripts/provision-db.sql \
  -v DbName="$DB_NAME" -v AppLogin="$APP_LOGIN" -v AppPassword="$APP_PASSWORD"
```

اسکریپت، پایگاه داده، لاگین سطح‌سرور، کاربر دیتابیس و عضویت `db_owner` روی **همان پایگاه** را می‌سازد (EF Core در استارت‌اپ مهاجرت می‌کند و به DDL نیاز دارد). اجرای دوباره بی‌خطر است: هر چیزی را تنها در صورت نبود می‌سازد. خروجی موفق، سطر `ready` است.

**۳) جدول‌ها:** مهاجرت EF Core به‌صورت خودکار در استارت‌اپ اعمال می‌شود؛ در اولین اجرا صفحه `/setup` ساخت اولین مدیر سامانه و بذرگذاری نقش‌ها، قالب‌های پیامک و دلایل تفکیک را انجام می‌دهد.

## ویزارد‌راه‌اندازی‌اولیه (`/setup`)

نصب یک‌بارمصرف است: تا وقتی پایگاه داده‌ای وجود ندارد و تا وقتی هیچ کاربری ساخته نشده، `/setup` باز است. اولین `POST /api/setup/initialize` موفق آن را برای همیشه می‌بندد و هر فراخوانی بعدی (از همان مرورگر یا با curl) `409 «راه‌اندازی اولیه قبلاً انجام شده است»` می‌گیرد.

| گام | چه می‌پرسد | مسیر |
|---|---|---|
| ۱) پایگاه داده | نام سرور، نام پایگاه داده، احراز هویت Windows یا SQL (کاربر + رمز)، timeout، `TrustServerCertificate`؛ در بخش «پیشرفته» رشته اتصال کامل که بر فیلدها اولویت دارد | `GET/POST /api/setup/database` |
| ۲) دامنه | سوییچ فعال‌سازی، `host`/`port`/`useSsl`، `domain`/`baseDn`، `bindDn` + `bindPassword`، timeout و فیلتر جست‌وجو | `POST /api/setup/initialize` |
| ۳) پیامک | **فقط سوییچ سراسری `sms.enabled`** تا روشن نشود هیچ فیلد دیگری نمایش داده نمی‌شود؛ پس از روشن کردن: `mode` (Api/Wsdl/Simulation)، endpoint و سازمان/خوشه، شناسه کاربری و رمز، شماره فرستنده، timeout، فاصله تلاش و سقف تلاش‌ها | همان‌جا |
| ۴) سازمان و مدیر | نام سازمان، لوگو، و حساب مدیر محلی (نام کاربری، نام، نام‌خانوادگی، موبایل، رمز ≥ ۸ نویسه) | همان‌جا |
| ۵) قواعد و ظاهر | قواعد مأموریت (فاصله ایمنی، افق آینده، خودبستن انصراف، یادآوری شروع)، سیاست نشست (مطلق/بی‌کارایی)، سربرگ/پاورقی و نمایش لوگوی حکم، اندازه کاغذ، مسیر فونت PDF، سطح لاگ | همان‌جا |
| ۶) تأیید | مرور همان چیزهایی که وارد کردید و ساخت سامانه | `POST /api/setup/initialize` |

**چه چیزی تضمین شده است:**

- **اتمیت.** هر شش گام در سرور با همان `SettingsWriters.Validate*` سنجیده می‌شوند که تب «تنظیمات» استفاده می‌کند — و این اعتبارسنجی **پیش از اولین نوشتن** انجام می‌شود. یک مقدار غلط یعنی «هیچ ردیفی نوشته نشد» و پیام فارسی دقیق همان فیلد در همان گام نمایش داده می‌شود؛ سامانه در حالت نیمه‌پیکربندی رها نمی‌شود.
- **گام دیتابیس واقعاً کار می‌کند.** `IDatabaseSetupProbe` پایگاه هدف را می‌سازد و مهاجرت را اعمال می‌کند، بعد رشته اتصال را اتمی در `~/.novafleet/bootstrap.json` می‌نویسد (tmp + move). نام پایگاه داده با `; = [ ] '` رد می‌شود.
- **دروازه ری‌استارت.** اگر منبع فعال رشته اتصال همان فایل نباشد — مثلاً `NOVAFLEET_ConnectionStrings__Default` یا `ConnectionStrings:Default` که بر فایل اولویت دارند — گام «ادامه» قفل می‌ماند، پیام «سرویس NovaFleet را راه‌اندازی مجدد کنید» نمایش داده می‌شود و `initialize` هم با `409` رد می‌شود؛ وگرنه تنظیمات روی پایگاه دیگری نوشته می‌شد.
- **اسرار یک‌طرفه‌اند.** `directory.bind-password` و `sms.password` فقط در ستون `ProtectedValue` (Data Protection) می‌نشینند، در ممیزی فقط `directoryBindPasswordSet` / `smsPasswordSet` به‌صورت بولی ثبت می‌شود و هیچ رمز — حتی در پاسخ `GET /api/setup/database` — به مرورگر برنمی‌گردد. فیلد خالی در ویرایش بعدی یعنی «دست نزن».
- **پیش‌پُر کردن.** گام ۱ از `GET /api/setup/database` سرور، نام پایگاه، نوع احراز هویت و نام کاربر SQL را از منبع فعال فعلی می‌گیرد (بدون رمز)، پس در اجرای مجدد ویزارد نیازی به تایپ دوباره نیست.
- **پس از نصب.** همه این مقادیر در تب «تنظیمات» (سازمان، قواعد، سیاست نشست، قالب حکم) و تب «اتصال سرویس‌ها» با مجوز `settings.connections.manage` قابل تغییرند؛ تنظیماتی که فقط در استارت‌اپ خوانده می‌شوند پیام صریح «نیاز به راه‌اندازی مجدد» برمی‌گردانند. نام و لوگوی سازمانی که در گام ۴ وارد می‌کنید، همان چیزی است که در نوار کنار و پیام خوش‌آمد پوسته نمایش داده می‌شود.

پوشش آزمون: `SetupWizardTests` در `tests/NovaFleet.UnitTests/Setup/` — نوشتن همه بلوک‌ها، بیرون‌نبودن اسرار از `Value` و ممیزی، اتمیت هنگام اعتبارسنجی ناموفق، رد رمز ضعیف، رد اجرای دوم، قفل گام دیتابیس پس از نصب، و سه حالت گام دیتابیس (ساخت/فعال، نیاز به ری‌استارت، رشته اتصال پیشرفته).

## داده‌نمونه‌و‌حساب‌های‌نمایشی

`scripts/seed-demo.sql` پایگاه را به یک محیط نمایشی کامل تبدیل می‌کند تا داشبورد، خط زمانی، گزارش‌ها و صف پیامک با داده واقعی به‌نظر برسند. این اسکریپت **بدون رمز** است؛ هش رمز حساب‌های نمونه به‌صورت متغیر sqlcmd از بیرون مخزن داده می‌شود.

**۱) ساخت هش رمز** (یک‌بار، بیرون از مخزن). رمز نمایشی همه حساب‌های `demo.*` این است:

```
Demo@1405!
```

هش را با الگوریتم خود سامانه (PBKDF2-SHA256، ۲۱۰٬۰۰۰ تکرار، ۱۶ بایت نمک تصادفی، ۳۲ بایت کلید — همان `Pbkdf2PasswordHasher`) بسازید و در فایلی بیرون از مخزن نگه دارید — مثال `C:\Users\<you>\.novafleet\mkhash.ps1`:

```powershell
$password = 'Demo@1405!'
$salt = [byte[]](1..16 | ForEach-Object { Get-Random -Maximum 256 })
$key  = [System.Security.Cryptography.Rfc2898DeriveBytes]::Pbkdf2(
          $password, $salt, 210000,
          [System.Security.Cryptography.HashAlgorithmName]::SHA256, 32)
'pbkdf2-sha256$210000$' + [Convert]::ToBase64String($salt) + '$' + [Convert]::ToBase64String($key) |
  Set-Content "$HOME\.novafleet\demo-hash.txt" -NoNewline -Encoding ascii
```

**۲) اجرا.** چون مسیر فایل در ویندوز باید با بک‌اسلش و خارج از زنجیره اسرار باشد، یک پوشش موقت بسازید (`C:\Users\<you>\.novafleet\seed-run.sql`):

```sql
:setvar DemoPasswordHash "<محتوای demo-hash.txt>"
:r C:\Users\<you>\Documents\...\scripts\seed-demo.sql
```

```bash
set -a; . "$HOME/.novafleet/db.env"; set +a
sqlcmd -S "$SQL_HOST" -U "$SA_USER" -P "$SA_PASSWORD" -d "$DB_NAME" \
  -f 65001 -b -i "C:\\Users\\<you>\\.novafleet\\seed-run.sql" -v CleanMode=1
```

| پارامتر | معنا |
|---|---|
| `CleanMode=1` | پیش از بارگذاری، **همه مأموریت‌ها**، درخواست‌های تغییر و صف پیامک پاک می‌شوند و رکوردهای نمونه قبلی (با پیش‌شونده `D0DE00…`) حذف می‌گردند |
| `CleanMode=0` | بارگذاری تنها؛ اگر بذر قبلاً خورده باشد، اسکریپت بدون تغییر خارج می‌شود |
| `-f 65001` | ورودی UTF-8؛ بدون آن متن فارسی خراب می‌شود |

**۳) چه داده‌ای ساخته می‌شود:**

| مجموعه | مقدار | نکته |
|---|---|---|
| رانندگان | ۳۱ نفر | هر راننده فعال خودروی اختصاصی هم‌شماره دارد؛ وضعیت استخدام، بایگانی و تلفن نمونه. فهرست پیش‌فرض `/api/drivers` بایگانی‌شده را نشان نمی‌دهد (۳۰ سطر) مگر `includeArchived=true` |
| خودروها | ۳۶ دستگاه | شامل تعمیرگاه/خارج از سرویس/بایگانی‌شده برای سنجش کارت‌های وضعیت ناوگان؛ فهرست پیش‌فرض ۳۵ سطر می‌دهد و یکی بایگانی است |
| مأموریت | ۵۵۱ مأموریت | طول از **۱ ساعت تا چند روز** (۶۰ تا ۵٬۷۰۰ دقیقه) |
| پخش زمانی | ۵۹ روز قبل تا ۶۰ روز بعد | بازه تصادفی **دو ماه قبل تا دو ماه آینده** نسبت به روز اجرا |
| توزیع وضعیت | ۲۱ در انتظار بررسی، ۱۰ در حال بررسی، ۲۶۳ تأییدشده، ۱۷ در حال اجرا، ۱۴۸ انجام‌شده، ۳۲ در انتظار انصراف، ۲۹ لغو، ۳۱ رد | همه وضعیت‌های چرخه عمر قابل مشاهده‌اند |
| درخواست تغییر | ۴۰ مورد | نزدیک‌ترین مأموریت‌ها به زمان اجرا، تا در داشبورد جلوه کنند |
| صف پیامک | ۱۲۰ مورد | با وضعیت‌های ارسال/تحویل/تلاش مجدد |
| واحدهای سازمانی و مقاصد | مجموعه نمونه | برای فیلترها و تأیید مقصد |
| تنظیم | `missions.future-request-days = 90` | تا مأموریت‌های دو ماه آینده در ویرایش رد نشوند |

**۴) قواعدی که داده نمونه رعایت کرده است** — همین قواعدی که خود سامانه تحمیل می‌کند:

- **هیچ راننده‌ای دو مأموریت هم‌پوشان ندارد**؛ برای هر راننده فعال یک «خط زمانه» از دو ماه قبل راه می‌افتد و مأموریت‌ها پشت هم، با فاصله بیکاری ۴۰ تا ۱۶۰ دقیقه، می‌چیند. بین خودروهای اختصاصی هم تداخلی نیست (تأیید با کوئری `LAG` روی `Missions`؛ خروجی `driverOverlaps = 0` و `vehicleOverlaps = 0`).
- **زمان‌ها فقط ساعت کامل به وقت تهران هستند** (`Mission.ValidateHour`)؛ بنابراین دقیقه UTC همه رکوردها `:30` است.
- **هیچ برچسب زمانی آینده ندارد**: `CreatedAtUtc`، `UpdatedAtUtc` و زمان بررسی/تأیید/تقسیم همگی پیش از لحظه اجرا محدود می‌شوند.
- **کیلومترشمار نزولی نیست**؛ مسافت هر مأموریت از تابع خطی زمان محاسبه می‌شود.
- شمارنده شماره مأموریت (`MissionNumberSequences`) با آخرین شماره هم‌گام می‌شود تا شماره‌گذاری دستی بعداً تکراری نشود.

**۵) حساب‌های نمایشی.** رمز همه این‌ها `Demo@1405!` است (فقط حساب‌های `demo.*`؛ حساب مدیر که در `/setup` ساختید و حساب دامنه، رمز خود شما را دارند و هیچ‌جا ثبت نمی‌شوند):

## پیکربندی

**دو خانواده تنظیمات وجود دارد** و قاعده تشخیصشان ساده است:

| خانواده | کجا زندگی می‌کند | کی خوانده می‌شود | مثال |
|---|---|---|---|
| بوت (bootstrap) | فایل‌های env بیرون از مخزن، `appsettings.json` و `~/.novafleet/bootstrap.json` | فقط هنگام استارت‌اپ | رشته اتصال، `Cors:AllowedOrigins`، `ASPNETCORE_URLS` |
| عملیاتی (runtime) | جدول `SystemSettings` در پایگاه داده | هر فراخوانی، زنده و بدون ری‌استارت | دامنه/LDAP، تنظیمات اتصال پیامک و سوییچ سراسری آن، قواعد مأموریت، سیاست نشست، برندینگ، سطح لاگ |

تنظیمات عملیاتی را مدیر سامانه از تب «تنظیمات» (و در نصب اولیه، از ویزارد `/setup`) می‌نویسد؛ راه نوشتن این ردیف‌ها پس از نصب `IRuntimeSettings` است، به‌جز ردیف‌های `sms.recipients.*` که `SmsService` مستقیم روی همان جدول می‌نویسد. ویزارد `/setup` هم از همان `SettingsWriters` (سازمان، دامنه، پیامک، عملیات، قواعد، سیاست نشست، قالب حکم) و فقط `setup.completed` را مستقیم می‌سازد، پس هیچ نوشتن تنظیماتی بدون ممیزی یا بدون اعتبارسنجی مشترک انجام نمی‌شود. ستون‌های `IsSecret = 1` مقدار خود را هرگز در `Value` نگه نمی‌دارند و متن‌مردها از طریق API به مرورگر برنمی‌گردد (فعل با «ذخیره شد» نشان داده می‌شود).

مقادیر پیش‌فرض در `src/NovaFleet.Api/appsettings.json` بی‌خطرند و هیچ رمزی ندارند:

```json
{
  "ConnectionStrings": { "Default": "" },
  "Sms": { "Mode": "Simulation" },
  "Cors": { "AllowedOrigins": [] }
}
```

**رشته اتصال** به یکی از چهار شکل (به همین اولویت، طبق `ConnectionStringResolver.Resolve` در `src/NovaFleet.Infrastructure/Setup/ConnectionStringResolver.cs:21`):

1. متغیر محیطی `NOVAFLEET_ConnectionStrings__Default` — بر همه چیز اولویت دارد تا نصب کپی‌شده روی ماشین دیگر بی‌سروصدا به تنظیمات ماشین قبلی برنگردد
2. `~/.novafleet/bootstrap.json` — فایلی که خودِ سامانه (ویزارد Setup و تب «اتصال سرویس‌ها») می‌نویسد؛ مسیر دقیقش از `GET /api/settings/connections/database` قابل خواندن است
3. `ConnectionStrings:Default` در `appsettings.json` / `appsettings.Development.json`
4. متغیرهای جداگانه `SQL_HOST` / `DB_NAME` / `APP_LOGIN` / `APP_PASSWORD` (مسیر قدیمی) — اگر هیچ‌کدام از سه مورد بالا خالی باشد، رشته اتصال از این چهارتا با `TrustServerCertificate=True` ساخته می‌شود

هیچ‌کدام تنظیم نشده ⇒ اپ با پیام صریح بالا نمی‌آید: «رشته اتصال تنظیم نشده است؛ …».

برای دستورات `dotnet ef` مسیر متفاوت است: `DesignTimeDbContextFactory` فقط متغیر `NOVAFLEET_CONNECTION_STRING` را می‌پذیرد و `ConnectionStrings:Default` را از فایل config نمی‌خواند.

**متغیرهای دیگر:**

| متغیر | مصرف |
|---|---|
| `ASPNETCORE_URLS` | آدرس گوش‌دادن API (پیش‌فرض توسعه: `http://localhost:5192`) |
| `ASPNETCORE_ENVIRONMENT` | `Development` برای فرانت‌دِو |
| `Cors:AllowedOrigins` | در تولید، آدرس دقیق فرانت‌اند (کوکی + CSRF) |

دو ترمینال لازم است.

```bash
# http://localhost:5192
```

**۲) فرانت‌اند:**

```bash
cd web
npm install
npm run dev
# http://localhost:5173
```

Vite مسیر `/api` را به `http://localhost:5192` پروکسی می‌کند، پس نیازی به تنظیم CORS در توسعه نیست. بعد از اولین اجرا، وارد صفحه `/setup` شوید و شش گام ویزارد را کامل کنید (گام ۱ با همان `SHAHABPC` و احراز هویت Windows، بدون رمز).

## نصب‌و‌اجرا‌در‌محیط‌عملیاتی

```bash
cd web && npm run build          # خروجی: web/dist  (tsc -b && vite build)
cp -r dist ../src/NovaFleet.Api/wwwroot   # پیش از publish
dotnet publish src/NovaFleet.Api -c Release -o ./publish
```

`Program.cs` تنها در صورتی از فرانت‌اند سرو می‌کند که پوشه `wwwroot` کنار API وجود داشته باشد؛ در آن حالت `UseDefaultFiles` + `UseStaticFiles` + `MapFallbackToFile("index.html")` فعال می‌شود و **یک‌دامنه‌ای** کار می‌کند: API و UI روی یک پورت، بدون نیاز به CORS. برای جداسازی، `Cors:AllowedOrigins` را روی آدرس دقیق فرانت‌اند تنظیم کنید.

سپس `publish/NovaFleet.Api.exe` را به‌عنوان سرویس ویندوز یا زیر IIS اجرا کنید. اگر API و فرانت‌اند جداگانه مستقر می‌شوند، هر دو باید پشت HTTPS و زیر یک دامنه باشند تا کوکی نشست و هدر CSRF درست کار کنند.

**HTTPS در تولید اجباری است.** هر محیطی جز `Development` (یعنی وقتی `ASPNETCORE_ENVIRONMENT` روی `Development` نیست) با `UseHsts()` + `UseHttpsRedirection()` بالا می‌آید و کوکی نشست پرچم `Secure` می‌گیرد؛ پس باید یک اندپوینت `https` واقعی وجود داشته باشد — گره HTTPS در IIS یا `ASPNETCORE_URLS` شامل `https://host:port` با گواهی معتبر (برای تست داخلی `dotnet dev-certs https --trust`). بدون آن، درخواست‌های `http` تغییر مسیر می‌خورند ولی به جایی نمی‌رسند و ورود هیچ‌وقت کوکی نمی‌گیرد. اگر شبکه داخلی عمداً بدون TLS کار می‌کند، تنها راه همان `ASPNETCORE_ENVIRONMENT=Development` است؛ این تصمیم را آگاهانه بگیرید.

## مدل‌امنیتی

- **احراز هویت:** محلی (PBKDF2-SHA256، ۲۱۰٬۰۰۰ تکرار، نمک ۱۶ بایت، کلید ۳۲ بایت) یا LDAP؛ هر دو پس از موفقیت یک نشست در پایگاه داده باز می‌کنند و پایان/خاتمه اجباری آن‌ها از صفحه امنیت ممکن است. تغییر رمز از `POST /api/auth/change-password` (حداقل ۸ نویسه) و برای کاربران دامنه مسدود است.
- **تلاش ناموفق:** هر ورود ناموفق یک `UserSession` با وضعیت Failed و یک سطر دفتر رویداد با دلیل («رمز یا نام کاربری نادرست»، «حساب غیرفعال است»، «حساب در گروه‌های مجاز نیست») ثبت می‌کند، بدون قفل کردن حساب — اگر قفل پس از N تلاش ناموفق لازم است، باید اضافه شود.
- **CSRF:** همه فراخوانی‌های تغییردهنده `/api` باید هدر `X-Requested-With: XMLHttpRequest` داشته باشند (مسیرهای `/api/auth` و `/api/setup` مستثنا).
- **حمل‌ونقل امن:** بیرون از `Development` همه درخواست‌های `http` با `307` به `https` می‌روند، `Strict-Transport-Security: max-age=2592000` روی پاسخ‌های امن می‌نشیند و کوکی `nf_session` همیشه پرچم `Secure` می‌گیرد (`CookieSecurePolicy.Always`). نتیجه: اگر پیکره‌بندی TLS جا بیفتد، سامانه بالا می‌آید ولی هیچ نشست ورودی بسته نمی‌شود. هر سه از یک پرچم `requireHttps` در `Program.cs` گره خورده‌اند و در پروفایل `http://localhost:5192` توسعه فعال نیستند.
- **رمزنگاری در حال انتقالِ ورود دامنه:** `LdapDirectoryAuthenticator` با `AuthType.Basic`.bind می‌کند و LDAPS فقط وقتی فعال است که مدیر `directory.use-ssl` را `true` گذاشته باشد؛ این تصمیم آگاهانه است و توضیحش در بخش [محدودیت‌های شناخته‌شده](#محدودیت‌های‌شناخته‌شده) آمده.
- **مجوزها:** `PermissionCatalog` چهل‌ودو کد دارد: یک کد `*` (همه دسترسی‌ها)، سه کد گروه مانند `missions.*` / `drivers.*` / `vehicles.*` و ۳۸ کد دانه‌درشت (`missions.approve`، `missions.print`، `notifications.sms.templates.manage`، `security.sessions.view`، `settings.system.manage`، `settings.connections.manage` …). نقش‌های پیش‌فرض: مدیر سامانه، مدیر ناوگان، اپراتور، درخواست‌کننده، ناظر. هر کاربر می‌تواند علاوه بر نقش، مجوز مستقیم (Grant/Deny) داشته باشد و نگاشت گروه دایرکتوری هم نقش اضافه می‌کند. منوی فرانت‌اند بر پایه همین کدها ساخته می‌شود، پس تبی که مجوزش را ندارید نمایش داده نمی‌شود.
- **سطح‌دسترسی داده:** درخواست‌کننده فقط مأموریت‌های خودش را می‌بیند؛ مدیر ناوگان و اپراتور کل محدوده را.
- **صف رویداد:** هر اقدام حساس با عامل، نتیجه و زمان (به وقت تهران) ثبت و قابل فیلتر است.
- **همزمانی:** ستون‌های `RowVersion` در خودرو و راننده، تغییر هم‌زمان دو اپراتور را به خطای ۴۰۹ تبدیل می‌کنند.
- **اسرار:** خارج از مخزن و رمزنگاری‌شده در دیتابیس. `bind-password` دامنه و `sms.password` با Data Protection (`ISecretProtector` در `src/NovaFleet.Infrastructure/Security/SecretProtector.cs`) در ستون `SystemSettings.ProtectedValue` (`nvarchar(max)`) می‌نشینند؛ حلقه کلید در `~/.novafleet/keys` است. نوشتن آن‌ها یک‌طرفه است (فیلد خالی = «تغییر نده»)، هیچ خواندن معمولی (`IRuntimeSettings.GetStringAsync` و-family) ردیف‌های `IsSecret` را برنمی‌گرداند، و در ممیزی فقط «رمز عوض شد» ثبت می‌شود، نه خودِ رمز. پاک‌کردن کلیدها یعنی از دست رفتن رمزها و لازم شدن ثبت مجددشان.
- **سوییچ سراسری پیامک:** کلید `sms.enabled`؛ نبودِ ردیف یا `false` بودنش یعنی خاموش. تا روشن نشود، `SmsQueueWorker` صف را دست‌نخورده رها می‌کند و «تست پیامک» با خطای اعتبارسنجی رد می‌شود؛ یعنی بدون تصمیم صریح مدیر، هیچ پیامک پولی از سامانه خارج نمی‌شود.

## محدودیت‌های‌شناخته‌شده

**۱) دروازه‌بانی مجوز (برطرف‌شده در این نسخه).** پیش از این، فقط بعضی سرویس‌ها `currentUser.Require(...)` داشتند و هیچ سیاست `RequireAuthorization` روی گروه `/api` وجود نداشت؛ نتیجه اینکه یک درخواست **بدون کوکی** می‌توانست تنظیمات را بخواند و بنویسد، کاربر مدیر بسازد، نقش‌ها را تغییر دهد، نشست‌ها را ختم کند و پیامک آزمایشی واقعی ارسال کند. اکنون سه لایه هم‌زمان بست بسته شده است:

- `RequireAuthorization` روی کل گروه `/api`؛ فقط `/api/setup/*` و `/api/auth/*` بی‌نیاز از نشست می‌مانند (راه‌اندازی اولیه قبل از وجود هر حسابی باید کار کند).
- `currentUser.Require(...)` در `SettingsService`، `SmsService`، `UserService`، `RoleService`، `SessionService` و `AuditQueryService`، با همان کدهایی که `PermissionCatalog` از قبل تعریف کرده و هیچ‌جا استفاده نمی‌شد (`settings.system.manage`، `settings.sessions`، `settings.mission-template.manage`، `settings.mission-split-reasons.manage`، `settings.authorization`، `users.manage`، `notifications.sms.view/.retry/.templates.manage`، `security.audit.view`، `security.sessions.view`).
- مجوز جدید `settings.connections.manage` برای تغییر و تست اتصال سرویس‌ها (دیتابیس، دامنه، پیامک، تنظیمات عملیاتی). `ConnectionsSettingsService` همان مجوز را روی هر چهار جفت `GET`/`PUT` مسیر `/api/settings/connections/*` و `ConnectionTestsService` روی هر سه مسیر `POST /api/settings/connections/*/test` بررسی می‌کند.

مسیرهای فنی که عمداً بی‌مجوز ماندند: `ISettingsService.GetValueAsync` (در اعتبارسنجی کوکی هر درخواست خوانده می‌شود؛ ردیف‌های `IsSecret` را ساختاراً برنمی‌گرداند)، `ISettingsService.GetRuntimeBundleAsync` (مسیر چاپ حکم، که مجوز خودش `missions.print` در `MissionService` سنجیده می‌شود و کاربر چاپ‌کننده نباید مجوز تنظیمات داشته باشد) و `ISessionService.ValidateAsync`/`ActiveCountAsync`. هیچ نوشتن تنظیماتی بدون رکورد ممیزی انجام نمی‌شود. پوشش آزمون: `AuthorizationGuardTests` و `RuntimeSettingsTests` در پروژه `NovaFleet.UnitTests`.

**۲) قفل حساب پس از تلاش ناموفق وجود ندارد**؛ فقط ثبت می‌شود. **۳) ارقام جدول گزارش‌ها لاتین است.** **۴) باندل فرانت‌اند code-split نشده است.**

**۵) ورود با دامنه بدون اجبارِ TLS کار می‌کند (تصمیم مدیر).** `LdapDirectoryAuthenticator` همیشه با `AuthType.Basic` bind می‌کند و `SecureSocketLayer` دقیقاً از `directory.use-ssl` می‌آید؛ نه ذخیره تنظیمات و نه خود احراز هویت، روشن‌بودن SSL را شرط نمی‌کنند. یعنی در حالت خاموش، هم رمز مدیر دامنه (BindDn) و هم رمز کاربر روی `POST /api/auth/login-ldap` در شبکه روشن می‌روند. پذیرفته شد چون شبکه مقصد بسته داخلی است؛ در هر شبکه‌ای که قابل شنود است، `directory.use-ssl` باید `true` باشد و گواهی DC نصب شود (بخش [احراز هویت با Active Directory](#احراز‌هویت‌با‌active‌directory)).

## احراز‌هویت‌با‌active‌directory

تنظیمات دامنه دیگر در فایل config یا متغیر محیطی نیستند؛ به‌عنوان ردیف‌های `directory.*` در جدول `SystemSettings` نگهداری می‌شوند و `LdapDirectoryAuthenticator` آن‌ها را در هر درخواست زنده می‌خواند (تغییر DC یا BaseDn نیاز به ری‌استارت ندارد). برای فعال کردن ورود با دامنه ویندوز، این مقادیر را در تب «تنظیمات ← اتصال سرویس‌ها» (`PUT /api/settings/connections/directory`، با مجوز `settings.connections.manage`) ثبت کنید — یا همان فرم را در گام ۲ ویزارد `/setup` («دامنه») پر کنید؛ اگر سوییچ فعال‌سازی خاموش بماند، ردیف `directory.enabled` با مقدار `False` نوشته می‌شود و اجبار `host`/`domain`/`baseDn` در اعتبارسنجی سنجیده نمی‌شود، پس ورود دامنه تا روشن‌کردن همان سوییچ مسدود است:

```json
{
  "enabled": true,
  "host": "dc1.corp.local",
  "port": 636,
  "useSsl": true,
  "domain": "Corp.Local",
  "baseDn": "DC=corp,DC=local",
  "bindDn": "svc_fleet",
  "bindPassword": "…",
  "timeoutSeconds": 15,
  "searchFilter": "(&(objectClass=user)(sAMAccountName={0}))"
}
```

| کلید دیتابیس | معنی |
|---|---|
| `directory.enabled` / `host` / `port` / `use-ssl` / `domain` / `base-dn` | اتصال و جست‌وجو؛ `host`/`domain`/`base-dn` فقط وقتی `enabled` است الزامی‌اند |
| `directory.bind-dn` / `directory.bind-password` | حساب سرویس اختیاری برای جست‌وجوی کاربران؛ **رمز فقط رمزنگاری‌شده ذخیره می‌شود و هرگز به UI برنمی‌گردد** |
| `directory.timeout-seconds` | مهلت bind و جست‌وجو (۱ تا ۱۲۰) |
| `directory.search-filter` | فیلتر LDAP؛ باید شامل `{0}` باشد و به‌جای آن نام کاربری با فرار LDAP جایگزین می‌شود (نه `string.Format`، پس `}` و `{` کاربر بی‌خطرند) |

`bindDn`/`bindPassword` اختیاری‌اند؛ برای جست‌وجوی کاربران لازم‌اند. در صورت نبود آن‌ها، ورود با UPN (`user@domain`) انجام می‌شود. سپس از صفحه ورود، تب «ورود با دامنه» یا `POST /api/auth/login-ldap` استفاده کنید.

**جریان ورود با دامنه:** سامانه با UPN (`user@Domain`) روی LDAP bind می‌شود، کاربر را در `BaseDn` جست‌وجو می‌کند، در صورت نبود یک حساب «دامنه‌ای» می‌سازد، عضویت‌های گروه را در `DirectoryGroupsJson` هم‌گام می‌کند و نقش‌ها را از نگاشت‌ها استخراج می‌کند. اگر هیچ نقشی به کاربر نرسد، دسترسی **رد** می‌شود (۴۰۳ «حساب شما در گروه‌های مجاز سامانه نیست») — یعنی bind موفق، ولی دسترسی نه.

**نگاشت گروه به نقش:** از صفحه امنیت یا `POST /api/roles/directory-mappings` با `groupName` و `roleId`. مقدار `groupName` می‌تواند کل DN یا فقط `CN` گروه باشد (مقایسه بی‌حساس به بزرگی/کوچکی حروف و بدون فاصله اضافه):

```json
{ "groupName": "تیم برنامه نویسی", "roleId": "…" }
```

**چرا دیگر متغیر محیطی `Directory__*` نمی‌خوانیم؟** چون `DirectoryOptions` و باندینگ `IOptions` حذف شده‌اند؛ تنها منبع، همان ردیف‌های `directory.*` است. یک `GET /api/settings/connections/directory` مقدارهای جاری را (بدون رمز) برمی‌گرداند و `PUT` آن‌ها را با رکورد ممیزی `UpdateDirectorySettings` جایگزین می‌کند. `RestartRequired` این مسیرها `false` است.

**LDAPS:** در حالت امن، `port = 636` و `useSsl = true` با اعتبارسنجی کامل گواهی سرور؛ این مسیر مستلزم آن است که DC واقعاً گواهی LDAPS نصب‌شده داشته باشد و نام سرور با `Subject` گواهی بخواند. اگر handshake برقرار نشود، اتصال با پیام «ارتباط با سرویس دایرکتوری برقرار نشد» رد می‌شود و باید یا گواهی DC کامل شود یا موقتاً LDAP ساده روی ۳۸۹ استفاده شود.

> مسیر دامنه در این نصب با LDAP ساده روی پورت ۳۸۹ و نگاشت گروه «تیم برنامه نویسی» → نقش «مدیر ناوگان» آزمایش و تأیید شده است: ورود از رابط کاربری، ساخت خودکار کاربر، دریافت ۲۵ مجوز مؤثر و ثبت نشست و رویدادها در دفتر امنیت.

## پیامک‌شبیه‌سازی‌و‌درگاه‌واقعی

### سوییچ سراسری: `sms.enabled`

اولین تصمیم درباره پیامک، انتخاب درگاه نیست؛ این است که اصلاً پیامکی از سامانه خارج شود یا نه. کلید `sms.enabled` تا وقتی مدیر روشنش نکند **خاموش شمرده می‌شود** (نه ردیفی seed شده و نه مقدار `true`) و تا `true` نشود:

- `SmsQueueWorker` صف را دست‌نخورده رها می‌کند (`ProcessQueueAsync` عدد صفر برمی‌گرداند؛ وضعیت پیامک‌ها `Queued` می‌ماند) و polling تحویل هم اجرا نمی‌شود؛
- دکمه «تست» / `POST /api/sms/test` با خطای اعتبارسنجی «ارسال پیامک در سامانه غیرفعال است؛ پیش از تست آن را فعال کنید.» رد می‌شود، حتی با مجوز کامل.

روشن/خاموش کردنش از `PUT /api/settings/connections/sms` با فیلد `enabled` و مجوز `settings.connections.manage` است و بلافاصله اعمال می‌شود (بی‌ری‌استارت). هدف: بدون تصمیم صریح مدیر، هیچ پیامک پولی ارسال نشود.

### تنظیمات اتصال درگاه

همین endpoint ردیف‌های `sms.*` را می‌نویسد؛ `GET` همان‌ها را بدون رمز برمی‌گرداند و به‌جای رمز، پرچم `hasPassword` را:

| کلید دیتابیس | فیلد API | معنا |
|---|---|---|
| `sms.enabled` | `enabled` | سوییچ سراسری بالا |
| `sms.mode` | `mode` | `Simulation` (پیش‌فرض) / `Wsdl` / `Api` |
| `sms.endpoint` | `endpoint` | آدرس سرویسدهنده؛ فقط در حالت‌های واقعی الزامی و باید http(s) مطلق باشد |
| `sms.organization` | `organization` | نام سازمان در سرویس پیامک |
| `sms.username` / `sms.password` | `username` / `password` | `password` فقط نوشته می‌شود (ستون رمزنگاری‌شده) و خالی بودنش یعنی «تغییر نده» |
| `sms.sender-number` | `senderNumber` | شماره فرستنده |
| `sms.timeout-seconds` | `timeoutSeconds` | ۱ تا ۱۲۰ |
| `sms.retry-minutes` / `sms.max-attempts` | `retryMinutes` / `maxAttempts` | فاصله تلاش مجدد (۱ تا ۱۴۴۰ دقیقه) و سقف تلاش (۱ تا ۲۰) |

`Simulation` هیچ تماس بیرونی نمی‌زند: پیامک در صف ثبت و در نخستین استعلام «تحویل‌شده» می‌شود، و تست اعتبار هم یک عدد ساختگی برمی‌گرداند. هر پیامک واقعی فقط با `Wsdl` ارسال می‌شود.

**درگاه `Wsdl` پیاده شده است** — `src/NovaFleet.Infrastructure/Sms/PayamSmsGateway.cs` مطابق بخش ۶ سند `docs/integrations/payam-sms-soap-v2.md`: SOAP 1.1 سبک RPC/encoded با namespace `urn:SMSAPIwsdl`، `Send` برای ارسال (شناسه سرور در `ProviderReference` می‌نشیند و بعداً با `getStatuses_OriginalID` رهگیری می‌شود)، `Balance` برای تست اتصال و هر ۲۱ کد خطای سند به دو دسته «تلاش دوباره بی‌فایده است» و «موقت است» تقسیم شده‌اند. شماره گیرنده پیش از فراخوانی به `98…` تبدیل می‌شود و اگر تبدیل‌ناپذیر باشد پیامک دائمی رد می‌شود؛ یعنی هیچ درخواستی با شماره خراب به سرویس‌دهنده نمی‌رود.

حالت درگاه هنگام هر فراخوانی از ردیف `sms.mode` خوانده می‌شود (`SmsGatewayRouter`)، پس تغییرش نیاز به ری‌استارت ندارد و نبودش یا هر مقدار ناشناخته به شبیه‌سازی می‌رسد تا یک تایپو، اعتبار واقعی حساب را خرج نکند. حالت `Api` در UI و تنظیمات پذیرفته می‌شود ولی فعلاً با پیام صریح رد می‌شود: قرارداد REST این سرویس‌دهنده در دست نیست، و فرمت ساختنِ حدسی برای آن درست نیست — با داشتن سند یا WSDL بخش REST، همین router فعال می‌شود.

رمز درگاه از انبار اسرار (`sms.password`، ستون رمزنگاری‌شده) خوانده می‌شود و فقط در پاکت ارسالی به سرویس‌دهنده قرار می‌گیرد؛ در `GET /api/settings/connections/sms` هرگز برگردانده نمی‌شود.

`SmsQueueWorker` ارسال، تلاش مجدد و خواندن وضعیت تحویل را مدیریت می‌کند و همه فواصلش را زنده از `SystemSettings` می‌خواند (`sms.retry-minutes`، `sms.polling-minutes`، `sms.max-polling-attempts`، `sms.reminder-minutes`)؛ از صفحه پیامک هم می‌توان دستی تلاش مجدد کرد یا با دکمه «تست» یک پیامک نمونه فرستاد. قالب‌ها برای هر رویداد (تأیید، تغییر، انصراف و …) قابل ویرایش‌اند و توکن‌های جلالی در آن‌ها هنگام ارسال تبدیل می‌شوند.

## اتصال‌سرویس‌ها‌و‌تست‌های‌زنده

تب هفتم تنظیمات — **«اتصال سرویس‌ها»**، فقط با مجوز `settings.connections.manage` — چهار کارت دارد و هر کارت (جز عملیات) یک دکمه تست زنده دارد که همان لحظه تماس واقعی می‌زند:

| کارت | مسیرهای تنظیم | تست | پیام موفق |
|---|---|---|---|
| پایگاه داده | `GET/PUT /api/settings/connections/database` | `POST /api/settings/connections/database/test` | «اتصال پایگاه داده برقرار است.» + `منبع فعال: {source}` و، در صورت وجود، «N مهاجرت اعمال‌نشده باقی مانده است» |
| دامنه (Active Directory) | `GET/PUT /api/settings/connections/directory` | `POST /api/settings/connections/directory/test?sampleUsername=` | «حساب Bind در دامنه پذیرفته شد و N کاربر در محدوده جست‌وجو یافت شد.» |
| سرویس پیامک | `GET/PUT /api/settings/connections/sms` | `POST /api/settings/connections/sms/test` و `POST /api/sms/test` | «سرویس پیامک اعتبار حساب را برگرداند.» + `اعتبار گزارش‌شده: X — حالت درگاه: Y` |
| عملیات | `GET/PUT /api/settings/connections/operations` | — (سطح لاگ و مسیر فونت فقط با restart معتبرند) | بنر «پس از راه‌اندازی مجدد سرویس اعمال می‌شود» |

**منبع رشته اتصال در تست مشخص می‌شود.** تست دیتابیس همان `ConnectionStringResolver` را صدا می‌زند که `Program.cs` در زمان بوت استفاده می‌کند، پس عددی را می‌آزماید که واقعاً فعال است (متغیر محیطی ← `bootstrap.json` ← `ConnectionStrings:Default`) و همان منبع را در پیام اعلام می‌کند. چون فایل بوت فقط در زمان بوت خوانده می‌شود، `RestartRequired` این کارت همیشه `true` است؛ رشته `GET` هم ماسک‌شده برمی‌گردد (`Password=` خالی) و به همین دلیل در فرم توضیح داده شده که برای ذخیره باید رشته کامل نوشته شود.

**جست‌وجوی دامنه با سقف اندازه انجام می‌شود.** `ProbeAsync` با حساب Bind وارد دامنه می‌شود و فیلتر تنظیمات را روی یک نام نمونه (`*` اگر خالی باشد) با `SizeLimit = 25` اجرا می‌کند. عدد گزارش‌شده «تعداد کاربر کل دایرکتوری» نیست؛ اگر به سقف برسد، پیام «حداقل ۲۵ کاربر یافت شد (سقف آزمون)» می‌گوید و اگر صفر باشد، پیام مستقیماً به `BaseDn` یا فیلتر جست‌وجو شک می‌کند — چون bind موفق با صفر کاربر معمولاً یعنی دامنه درست و محدوده جست‌وجو غلط. کد خطای LDAP ۴۹ («اعتبارنامه رد شد») از بقیه خطاها جدا می‌شود تا مشخص باشد مشکل رمز است نه شبکه.

**`Balance` صادق است.** در حالت `Simulation` اعتبار ساختگی برمی‌گردد و پیام صریحاً «حالت درگاه: Simulation» را می‌چاپد تا با درگاه واقعی اشتباه نشود؛ در حالت ناپیاده‌شده `Api` تست **شکست می‌خورد** (پیش‌تر همان عدد ساختگی را برمی‌گرداند). اگر کلید سراسری `sms.enabled` خاموش باشد، پیام تست همان را با «کل سامانه پیامک خاموش است» یادآوری می‌کند — یعنی تست سبز به معنی اجازه ارسال نیست. برای اطمینان از مسیر ارسال، «ارسال آزمایشی» همان `POST /api/sms/test` را می‌زند و پیامک در صفحه `/sms` قابل ردیابی است.

**چه چیزی بیرون نمی‌رود.** هیچ‌یک از پاسخ‌های تست رمز ذخیره‌شده را برنمی‌گرداند: خطای سرویس‌دهنده قبل از نمایش کوتاه و پاک‌سازی می‌شود و رکورد ممیزی فقط `Test = Database|Directory|Sms` همراه با `Success` و `Detail` غیرحساس را نگه می‌دارد. هر تست، مستقل از نتیجه، یک رویداد `TestConnection` در دفتر امنیت ثبت می‌کند (موفقیت هم ممیزی می‌شود، چون نشان می‌دهد کسی تنظیمات اتصال را آزموده است).

**ری‌استارت درون‌برنامه‌ای انجام نمی‌شود.** هیچ `IOptionsMonitor` و هیچ مسیر «restart» وجود ندارد؛ سامانه عمداً فقط پیام می‌دهد و مدیر سرویس را بیرون از UI راه‌اندازی مجدد می‌کند. تنظیمات دیتابیس‌محور (`directory.*`، `sms.*`، `mission.*`، سیاست نشست) بی‌ری‌استارت اعمال می‌شوند؛ `operations.log-level`، `operations.pdf-font-path` و رشته اتصال نه.

## چرخه‌عمر‌مأموریت

```
۱ در انتظار بررسی
  → شروع بررسی → ۲ در حال بررسی
      → تأیید و تخصیص → ۳ تأییدشده → شروع اجرا → ۴ در حال اجرا
          → پایان / ثبت کیلومتر → ۵ انجام‌شده
          → خاتمه زودهنگام → ۵ با یادداشت
          → درخواست انصراف → ۶ در انتظار انصراف → تأیید/رد
      → رد → ۸ ردشده
  لغو (۷) از هر حالتی که به مرحله انجام/لغو/رد نرسیده باشد
```

تغییرات میانی مسیر (تمدید، تعویض راننده/خودرو، تفکیک) به‌صورت «درخواست تغییر» ثبت و جداگانه بررسی/تصمیم می‌شوند تا سوابق حفظ شود. **کنترل تداخل** همیشه بر پایه زمان برنامه‌ریزی‌شده و با در نظر گرفتن فاصله ایمنی است، نه صرف وجود یک مأموریت فعال.

## گزارش‌ها‌و‌خروجی‌ها

- `GET /api/reports` تعریف گزارش‌ها را برمی‌گرداند.

- `GET /api/missions/{id}/order.pdf` سند حکم مأموریت (نیازمند مجوز `missions.print`) را inline در مرورگر باز می‌کند؛ سربرگ، لوگو و پاورقم از تنظیمات سازمان و قالب حکم می‌آیند.

**مجوز:** اجرای هر گزارش `reports.view` می‌خواهد و دانلود فایل `reports.export`. در نقش‌های seed شده تنها **مدیر ناوگان** هر دو را دارد (مدیر سامانه با `*` همه چیز را)؛ اپراتور، درخواست‌کننده و ناظر عمداً بدون گزارش‌اند — اگر ناظر شما گزارش می‌خواهد، مجوز مستقیم Grant کنید.

|---|---|---|
| `missions` | ۵۲۹ | ۹ |
| `missions-distance` | ۲۶ | ۳ |
| `driver-activity` | ۲۶ | ۴ |
| `vehicle-usage` | ۲۶ | ۴ |
| `org-unit` | ۶ | ۵ |
| `mission-status` | ۸ | ۲ |

**قاعده پیاده‌سازی (مهم برای توسعه بعدی):** در `ReportService` فیلترها باید تا آخرین مرحله روی `IQueryable<Mission>` بمانند و پرتاب به رکورد گزارش (`MissionReportRow`) باید **بعد** از `Where` باشد. اگر برعکس شود، EF Core نمی‌تواند predicate را به SQL ترجمه کند و `InvalidOperationException` — یعنی خطای ۵۰۰ — می‌دهد. `Filtered()` فیلترها را می‌زند و `LoadRowsAsync()` یک‌بار با join راننده/خودرو به رکورد گزارش پرتاب می‌کند؛ گروه‌بندی‌ها روی همان فهرست در حافظه انجام می‌شود.

**مهاجرت جدید** (رشته اتصال فقط از متغیر محیطی، نه از فایل):

## خط زمانی

`GET /api/timeline?fromUtc=&toUtc=&driverId=&vehicleId=` مأموریت‌هایی را برمی‌گرداند که با بازه درخواست هم‌پوشانی زمانی دارند (وضعیت‌های ۱، ۲، ۳، ۴، ۵ و ۶؛ لغو و ردشده عمداً نمایش داده نمی‌شوند).

نمایش در `web/src/pages/TimelinePage.tsx`:

- **یک ردیف برای هر راننده.** ردیف «بدون راننده» درخواست‌های تخصیص‌نیافته را نگه می‌دارد. اگر گزینه «فقط رانندگانی که در این بازه مأموریت دارند» خاموش باشد، رانندگان بیکار هم با برچسب «بدون مأموریت» لیست می‌شوند.
- **زوم پیوسته از یک ساعت تا دو ماه.** پنج مقیاس با پیکسل بر ساعت تعریف می‌شود: ساعت `۲۴`، روز `۲٫۷`، هفته `۱٫۰۸`، ماه `۰٫۴۵`، فصل `۰٫۱۸`. سلول‌های سرِ جدول خودکار تغییر granularity می‌دهند: در مقیاس ساعت هر خانه یک ساعت است، در روز/هفته یک روز، و در ماه/فصل یک هفته.
- **تناسب خودکار بازه با مقیاس.** با تغییر زوم، بازه حول مرکز فعلی آنقدر کوچک یا بزرگ می‌شود که عرض ریل بین ۶۲۰ تا ۶۲۰۰ پیکسل بماند؛ برای همین زوم «ساعت» روی بازه سه‌هفته‌ای، صفحه را نمی‌شکند. شش دکمه «بازه سریع» (یک روز تا دو ماه) نیز هرکدام زوم مناسب خودش را می‌چیند.
- **پر کردن عرض یا اسکرول، خودکار.** عرض ریل با `ResizeObserver` اندازه گرفته می‌شود؛ اگر جمع ستون‌ها کمتر از فضای موجود باشد همه ستون‌ها با یک ضریب یکسان بزرگ می‌شوند تا ریل تا لبه صفحه پر شود، و اگر بیشتر باشد ضریب روی ۱ می‌ماند و اسکرول افقی فعال می‌شود. ستون نام راننده (`۱۹۰px`) در مقیاس حساب نمی‌آید و نوارها، خط «اکنون» و باند ماه‌ها هم با همان ضریب مقیاس می‌خورند، پس هیچ‌وقت نوار از ریل بیرون نمی‌زند.
- **برش نوار در لبه‌های پنجره**؛ مأموریت چندروزه‌ای که نیمی‌اش بیرون بازه است، تا لبه بریده می‌شود و از ردیف بیرون نمی‌زند. عرض حداقلی ۱۰ پیکسل دارد تا مأموریت یک‌ساعته در مقیاس ماه هم کلیک‌پذیر بماند.
- **کلیک = دیدن و ویرایش.** مدال سریع، اطلاعات کامل (وضعیت، نوع، درخواست‌کننده، راننده، خودرو، زمان‌ها، مسافت) را نشان می‌دهد و اگر مأموریت در وضعیت «در انتظار بررسی» و کاربر مجوز `missions.edit` داشته باشد، عنوان/مبدأ/مقصد/تاریخ و ساعت شروع و پایان را همان‌جا با `PUT /api/missions/{id}` ذخیره می‌کند. برای وضعیت‌های دیگر مدال راهنمای «درخواست تغییر» را نشان می‌دهد و لینک «صفحه مأموریت» همیشه هست.
- **خط «اکنون»** و سایه آخر هفته‌ها (`جمعه`) روی ریل؛ برچسب روز و ماه جلالی، ساعت‌ها با ارقام فارسی.

## کارهای‌انجام‌شده‌در‌این‌نسخه

**مخزن و معماری**

- ساخت کامل راه‌حل چهارلایه `NovaFleet.sln` (Domain / Application / Infrastructure / Api) با Build بدون warning و خطا، به‌همراه پروژه‌های تست خالی `tests/NovaFleet.UnitTests` و `tests/NovaFleet.IntegrationTests`.
- پیاده‌سازی موجودیت‌ها و قواعد دامنه: مأموریت، راننده، خودرو، مقصد، واحد سازمانی، کاربر/نقش/مجوز، صف پیامک، قالب‌ها، درخواست تغییر، دفتر رویداد و تنظیمات.

**بک‌اند**

- ۱۱۱ endpoint (۳۹ GET، ۵۲ POST، ۱۸ PUT، ۲ DELETE) در `EndpointMapper` برای مأموریت، راننده، خودرو، مقصد، پیامک، گزارش، امنیت، تنظیمات، اتصال سرویس‌ها، سازمان، تایم‌لاین و ویزارد نصب.
- احراز هویت محلی + LDAP، نشست‌های کوکی‌محور با پایان اجباری، ثبت هر تلاش ناموفق در نشست و دفتر رویداد، هدر CSRF، و ۴۲ کد مجوز در `PermissionCatalog` (یک `*`، سه گروه `x.*` و ۳۸ کد دانه‌درشت) با Grant/Deny مستقیم و نگاشت گروه دایرکتوری به نقش.
- چرخه عمر کامل مأموریت: ثبت → بررسی → تأیید و تخصیص → اجرا → پایان/خاتمه زودهنگام، به‌همراه انصراف، لغو، رد، تمدید، تعویض راننده/خودرو و تفکیک؛ همه با کنترل تداخل راننده و خودرو و فاصله ایمنی قابل تنظیم.
- دو Worker پس‌زمینه: انتقال خودکار وضعیت/آزادسازی منابع، و ارسال و پیگیری تحویل پیامک با تلاش مجدد.
- خروجی: حکم مأموریت PDF راست‌به‌چپ با QuestPDF، گزارش‌های پارامتری Excel (ClosedXML) و PDF.
- تقویم جلالی سمت سرور با `PersianCalendar` و مبنای وقت تهران (+۳:۳۰)؛ دامنه فقط ساعت کامل تهران را می‌پذیرد.

**فرانت‌اند و طراحی**

- تم «Emerald Premium» (سبز زمردی/طلایی، وزیرمتن، RTL کامل، دسترس‌پذیری کیبورد و فاصله رنگ) و کتابخانه کامپوننت‌های `card/btn/input/badge/modal/…`.
- صفحه‌ها: داشبورد با نمودارهای Recharts و ارقام فارسی، لیست و جزئیات مأموریت، رانندگان، خودروها (کارت وضعیت با تفکیک آمادگی ذاتی از درگیری زمانی)، مقاصد، پیامک، گزارش‌ها، امنیت (کاربران/نقش‌ها/نشست‌ها/دفتر رویداد)، تنظیمات و خط زمانی.
- اصلاح‌های این دوره: تداخل متن کارت وضعیت خودرو با نمودار برطرف شد؛ محورهای نمودارها فارسی شدند؛ دو اشکال مشترک تبدیل تاریخ/ساعت (`toJalali` و `formatFaDateTime`) که ساعت را دوباره جابه‌جا می‌کرد اصلاح شد.
- رفع خطای ۵۰۰ در شش گزارش مأموریتی (`missions`، `missions-distance`، `driver-activity`، `vehicle-usage`، `org-unit`، `mission-status`): در `ReportService` فیلترها باید روی خودِ موجودیت `Mission` اعمال شوند و پرتاب به رکورد گزارش باید **آخرین** مرحله باشد، وگرنه EF Core نمی‌تواند `Where` را به SQL ترجمه کند و `InvalidOperationException` می‌دهد. اکنون `Filtered()` فیلترها را می‌زند و `LoadRowsAsync()` یک‌بار با join راننده/خودرو به `MissionReportRow` پرتاب می‌کند؛ گروه‌بندی‌ها روی همین فهرست در حافظه انجام می‌شود.

- پایگاه `NovaFleetDb` روی SQL Server ساخته شد (لاگین برنامه با `db_owner` روی همین پایگاه) و مهاجرت EF Core اعمال شد.
- `scripts/seed-demo.sql` نوشته و اجرا شد: ۳۱ راننده، ۳۶ خودرو، ۵۵۱ مأموریت با طول ۱ ساعت تا چند روز روی بازه دو ماه قبل تا دو ماه آینده، ۴۰ درخواست تغییر و ۱۲۰ پیامک — بدون هیچ هم‌پوشانی راننده یا خودرو، بدون برچسب آینده، بدون کیلومتر نزولی و با ساعت کامل تهران.
- مسیر ورود با دامنه روی LDAP ساده تست و تأیید شد (ورود، ساخت خودکار کاربر، نگاشت گروه به نقش، ثبت نشست و رویداد).
- جریان «کلیک روی نوار تایم‌لاین → مشاهده → ویرایش → ذخیره» روی API واقعی و رابط کاربری آزمایی شد (ذخیره و سپس بازگردانی مقدار).

**امنیت و تنظیمات (دوره جاری)**

- بستن شکاف دروازه‌بانی: `RequireAuthorization` روی کل گروه `/api` (به‌جز `/api/auth/*` و `/api/setup/*`) به‌علاوه `currentUser.Require(...)` در `SettingsService`، `SmsService`، `UserService`، `RoleService`، `SessionService` و `AuditQueryService`؛ جزئیات و استثناهای عمدی در بخش [محدودیت‌های شناخته‌شده](#محدودیت‌های‌شناخته‌شده).
- بستن کوکی نشست به TLS: بیرون از `Development`، `nf_session` با `CookieSecurePolicy.Always` می‌نشیند و `UseHsts()` + `UseHttpsRedirection()` فعال می‌شوند (تأیید زنده: `http` → `307` به `https` و هدر `Strict-Transport-Security: max-age=2592000`). پروفایل `http://localhost:5192` توسعه دست‌نخورده ماند، چون هر سه از `IHostEnvironment.IsDevelopment()` گره می‌خورند.
- تنظیمات runtime دیتابیس‌محور: `IRuntimeSettings` + `RuntimeSettings` مسیر همگانی نوشتن جدول `SystemSettings` شد و پشته‌ای مثل `LdapDirectoryAuthenticator` از `IOptions` به خواندن زنده ردیف‌های `directory.*` منتقل شد (بدون ری‌استارت).
- اسرار با Data Protection (بدون پکیج NuGet جدید، از طریق `FrameworkReference` به `Microsoft.AspNetCore.App`): `ISecretProtector`/`DataProtectionSecretProtector`، ستون `SystemSettings.ProtectedValue` با مهاجرت `AddProtectedSystemSettings`، فیلدهای نوشتنی-یک‌طرفه و حلقه کلید `~/.novafleet/keys`.
- `GET/PUT /api/settings/connections/{directory,sms,operations,database}` با اعتبارسنجی، ممیزی و `RestartRequired` صادقانه؛ `GET` رشته اتصال ماسک‌شده می‌دهد و منبع فعال را اعلام می‌کند.
- رشته اتصال از سه منبع با اولویت خوانده می‌شود (`ConnectionStringResolver`) و فایل بوت‌استرپ `~/.novafleet/bootstrap.json` اتمی نوشته می‌شود تا ویرایش اتصال پس از نصب ممکن باشد.
- سوییچ سراسری `sms.enabled` (پیش‌فرض خاموش): کارگر صف و «تست پیامک» هر دو از همان تصمیم عبور می‌کنند.
- درگاه payamSMS نسخه ۲ (`PayamSmsGateway`، SOAP 1.1 RPC/encoded مطابق `docs/integrations/payam-sms-soap-v2.md`) با `Send`/`getStatuses_OriginalID`/`Balance`، نگاشت ۲۱ کد خطا به دائم/موقت، نرمال‌سازی شماره به `98…`، و انتخاب حالت از `sms.mode` توسط `SmsGatewayRouter` بی‌ری‌استارت. `SmsOptions`/`AdpSmsGateway` و بخش `Sms` در `appsettings.json` حذف شدند؛ `sms.max-attempts` هم واقعاً سقف تلاش‌های مجدد صف شد.
- ویزارد شش‌گامی `/setup`: گام دیتابیس (`GET/POST /api/setup/database` — ساخت و مهاجرت واقعی، نوشتن `~/.novafleet/bootstrap.json`، پیش‌پُر کردن از منبع فعال بدون برگرداندن رمز، و درواز restart تا سرویس روی همان پایگاه بالا نیاید) و پنج گام بعدی که در تأیید نهایی با همان `SettingsWriters` اعتبارسنجی و سپس نوشته می‌شوند: دامنه، پیامک (فیلدها فقط وقتی سوییچ سراسری روشن شود)، سازمان و مدیر محلی، قواعد/نشست/قالب/ظاهر، و خلاصه.
- پوسته حالا نام و لوگوی سازمانی را از `organization.name` / `organization.logoDataUrl` می‌خواند (نوار کنار و پیام خوش‌آمد) به‌جای رشته ثابت «ناوگان نوین»؛ چون از همان `queryKey: ['settings']` استفاده می‌کند، با ذخیره در تب تنظیمات بی‌ری‌استارت عوض می‌شود.
- آزمودن زنده نصب از صفر: wipe کامل، شش گام در مرورگر، و سپس بررسی مستقیم پایگاه — ۳۵ ردیف `SystemSettings`، دو راز با `IsSecret=1` و `ProtectedValue` (هیچ مقداری در `Value`)، مدیر محلی با هش PBKDF2 و دو سطر ممیزی که فقط `*PasswordSet` را نشان می‌دهند. یک گام با مقدار نادرست (endpoint بدون `http`) به ۴۰۰ رسید و هیچ ردیفی ننوشت — اتمیت در محیط واقعی تأیید شد.
- تب «اتصال سرویس‌ها» در تنظیمات با چهار کارت (دیتابیس، دامنه، پیامک، عملیات) و سه تست زنده: `POST /api/settings/connections/database/test` (اتصال واقعی + مهاجرت‌های معوق + منبع فعال رشته اتصال)، `.../directory/test` (bind با حساب سرویس و جست‌وجوی نمونه تا سقف ۲۵ کاربر همراه شمارش نتیجه) و `.../sms/test` (`Balance` درگاه فعال)؛ «ارسال آزمایشی» هم از همان‌جا پیامک را در صف می‌گذارد. هر تست یک رویداد `TestConnection` در دفتر امنیت می‌نویسد و هیچ‌کدام رمز ذخیره‌شده را برنمی‌گرداند. بنر restart فقط برای تنظیمات واقعاً ری‌استارت‌محور (سطح لاگ، مسیر فونت، رشته اتصال) نمایش داده می‌شود.
- `SmsGatewayRouter.GetBalanceAsync` در حالت ناپیاده‌شده `Api` دیگر اعتبار ساختگی برنمی‌گرداند و با پیام صریح رد می‌شود — تست اتصال نباید دروغ بگوید.
- رفع باگ «انتخاب تصویر» لوگو در تب سازمان و ویزارد: چون مقدار `input type=file` پاک نمی‌شد، انتخاب دوباره همان فایل (مثلاً پس از «حذف») هیچ `change` ای روشن نمی‌کرد و دکمه «کار نمی‌کرد»؛ حالا مقدار پس از هر انتخاب صفر می‌شود و با `pointer-events-none` روی خود input، فقط برچسب فعال می‌شود.
- ۱۶۹ آزمون سبز در `NovaFleet.UnitTests` روی SQLite در حافظه، از جمله `AuthorizationGuardTests`، `RuntimeSettingsTests`، `ConnectionTestsServiceTests`، `PayamSmsGatewayTests` و `SetupWizardTests`.

**باقی‌مانده**

- باندل فرانت‌اند یک تکه است (~۹۰۰ کیلوبایت، gzip ≈ ۲۵۵)؛ code-splitting با `React.lazy` ارزش انجام دارد.
- حالت `Api` درگاه پیامک در تنظیمات پذیرفته می‌شود ولی ارسال نمی‌کند: قرارداد REST سرویس‌دهنده در مخزن سند نشده است و حدس زدن فریم‌ورک سیم درست نیست. با رسیدن WSDL/سند REST، همان `SmsGatewayRouter` بدون تغییر معماری فعال می‌شود؛ فعلاً مسیر واقعی `Wsdl` است.
- درگاه payamSMS هنوز روی سرویس‌دهنده زنده (با اعتبار واقعی) آزمایش نشده؛ آزمون‌ها با `HttpMessageHandler` ساختگی‌اند.
- نوشتن تنظیمات اتصال روی HTTP واقعی با نشست معتبر برای مسیر پیامک آزموده شد؛ `PUT` دیتابیس (چون فایل بوت را بازمی‌نویسد و restart می‌خواهد) و `PUT` دامنه (چون DC در این محیط نیست) فقط در آزمون واحد پوشش دارند (`RuntimeSettingsTests`).
- `NovaFleet.IntegrationTests` هنوز هیچ آزمونی ننوشته است.
- چهار یافته ممیزی امنیتی این دوره عمداً باز ماند (انتخاب مدیر، در مقابلِ فقط بستن حمل‌ونقل نشست): اعتبارسنجی `sms.endpoint` در هر ذخیره و بستن بازخورد خام سرویس‌دهنده (SSRF با کوئری از شبکه داخلی)، کف تعداد تکرار PBKDF2 به‌جای پذیرش عددِ داخل رشته هش، محدودسازی نرخ ورود بی‌نام (rate limit؛ بدون قفل حساب)، و اعتبارسنجی اندازه/نوع لوگوی ارسالی. اجبار LDAPS هم بررسی و کنار گذاشته شد؛ دلیل و ریسکش در بند ۵ بخش [محدودیت‌های شناخته‌شده](#محدودیت‌های‌شناخته‌شده).
- ارقام جدول گزارش‌ها با ارقام لاتین چاپ می‌شوند؛ برای یکدستی با بقیه رابط، فارسی‌کردن آن‌ها در `ReportService` باقی است.
- فایل مجوز (LICENSE) به مخزن اضافه نشده است؛ تا پیش از آن، شرایط بخش [مجوز](#مجوز) حاکم است.
