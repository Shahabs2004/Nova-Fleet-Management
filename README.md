## پشته‌فناوری

- **بک‌اند:** ASP.NET Core 10 (Minimal API)، EF Core 10، SQL Server
- **معماری:** Clean Architecture چهارلایه (Domain ← Application ← Infrastructure ← Api)
- **احراز هویت:** کوکی `nf_session` + هدر CSRF + هش رمز PBKDF2-SHA256 + مجوزهای مبتنی بر کد
- **فرانت‌اند:** React 19، TypeScript، Vite 8، Tailwind CSS 4، React Query، React Router 7، Recharts
- **خروجی:** QuestPDF ( سند حکم و گزارش PDF )، ClosedXML ( Excel )
- **پشت‌زمینه:** `MissionLifecycleWorker` (انتقال خودکار وضعیت و آزادسازی منابع) و `SmsQueueWorker` (ارسال و بررسی تحویل)
- **طراحی:** تم «Emerald Premium» — سبز زمردی `#0F766E`، طلایی `#C8A44A`، سطح `#F6F8F7`، فونت وزیرمتن، کاملاً RTL

## ساختارمخزن

```
NovaFleet.sln
src/
  NovaFleet.Domain/            موجودیت‌ها، حالت‌ها و قواعد کسب‌وکار
  NovaFleet.Application/       سرویس‌ها، DTOها، مجوزها و انتزاع‌ها
  NovaFleet.Infrastructure/    EF Core، LDAP، درگاه پیامک، PDF، احراز هویت
  NovaFleet.Api/               Program.cs، endpointها، میدل‌ور، Workerها
web/                           فرانت‌اند React (صفحه‌ها، کامپوننت‌ها، استایل Emerald)
scripts/provision-db.sql       ساخت پایگاه داده، لاگین برنامه و نقش‌دسترسی‌ها
scripts/seed-demo.sql          داده نمایشی (راننده، خودرو، مأموریت، پیامک)
tests/                         پروژه‌های NovaFleet.UnitTests و NovaFleet.IntegrationTests
docs/screenshots/              تصویرهای همین README
```

> پوشه `src/NovaFleet.Api/wwwroot/` میزبان خروجی build فرانت‌اند در حالت یکپارچه است؛ در محیط توسعه لازم نیست چیزی داخل آن باشد.

## پیش‌نیازها

| ابزار | نسخه مورد نیاز | بررسی با |
|---|---|---|
| .NET SDK | ۱۰.۰.۴xx (کلید `global.json` روی `10.0.403` با `rollForward: latestFeature` قفل شده) | `dotnet --version` |
| Node.js | ۲۰ یا بالاتر (توسعه روی ۲۴ انجام شده) | `node -v` |
| SQL Server | ۲۰۱۹ یا بالاتر، با احراز هویت ترکیبی (لاگین `sa`) | `SELECT @@VERSION` |
| sqlcmd | هر نسخه با پشتیبانی `-i` و `-v` | `sqlcmd -?` |
| فونت Tahoma | فقط برای خروجی PDF فارسی | مسیر `C:\Windows\Fonts\tahoma.ttf` |

> **محدودیت SQL Server 2019:** این نسخه `AT TIME ZONE 'Asia/Tehran'` را نمی‌شناسد، بنابراین همه محاسبات وقت تهران (`+۳:۳۰`) در EF Core با `DATEADD(MINUTE, ±210, …)` ترجمه می‌شوند. روی SQL Server 2022 به بعد هم همین کوئری‌ها درست کار می‌کنند و تغییری لازم نیست.

## راه‌اندازی‌کامل‌پس‌از‌دانلود

هشت گام، از clone تا اولین ورود. کدها برای Git Bash روی ویندوز نوشته شده‌اند؛ تفاوت معادل PowerShell یا لینوکس فقط در مسیرها و جداکننده‌های فایل env است.

**۱) دریافت مخزن و پیش‌خوانی build**

```bash
git clone https://github.com/Shahabs2004/Nova-Fleet-Management.git
cd Nova-Fleet-Management
dotnet build          # باید بدون warning و error تمام شود
cd web && npm install && cd ..
```

`dotnet build` راه‌حل چهارلایه و دو پروژه تست را می‌سازد. `npm install` فقط برای محیط توسعه لازم است؛ در حالت production خروجی از `npm run build` به `wwwroot` کپی می‌شود.

**۲) ساخت پوشه اسرار (بیرون از مخزن)**

```bash
mkdir -p "$HOME/.novafleet"
```

سه فایل در این پوشه می‌نشیند: `db.env` (برای اسکریپت راه‌اندازی)، `app.env` (برای اجرای اپلیکیشن) و `ldap.env` (اختیاری، فقط تست دستی دامنه). شکل هر سه در بخش [راه‌اندازی پایگاه داده](#راه‌اندازی‌پایگاه‌داده) آمده است. **هیچ‌کدام داخل مخزن نمی‌آید و هیچ رمزی در فایل‌های پروژه وجود ندارد.**

**۳) ساخت پایگاه داده، لاگین برنامه و جدول‌ها**

```bash
set -a; . "$HOME/.novafleet/db.env"; set +a
sqlcmd -S "$SQL_HOST" -U "$SA_USER" -P "$SA_PASSWORD" \
  -i scripts/provision-db.sql \
  -v DbName="$DB_NAME" -v AppLogin="$APP_LOGIN" -v AppPassword="$APP_PASSWORD"
```

اسکریپت، پایگاه `NovaFleetDb`، لاگین سطح‌سرور برای برنامه (`CHECK_POLICY = ON`) و کاربر همان دیتابیس را می‌سازد و آن را عضو `db_owner` **همان پایگاه** می‌کند؛ این سطح لازم است چون مهاجرت EF Core در استارت‌اپ جدول می‌سازد. لاگین به هیچ پایگاه یا سرور دیگری دسترسی ندارد و اجرای دوباره اسکریپت بی‌خطر است. جدول‌ها را هنوز چیزی نساخته‌اید؛ مهاجرت EF Core در گام بعد خودکار اعمال می‌شود.

**۴) اجرای API**

```bash
set -a; . "$HOME/.novafleet/app.env"; set +a
ASPNETCORE_URLS=http://localhost:5192 dotnet run --project src/NovaFleet.Api
```

در استارت‌اپ، `DatabaseInitializer` دو کار می‌کند: `db.Database.MigrateAsync()` (ساخت همه جدول‌ها) و بذرگذاری idempotent پنج نقش، چهار دلیل تفکیک و نه قالب پیامک. اگر رشته اتصال تنظیم نشده باشد، اپ با پیام «رشته اتصال تنظیم نشده است» بالا نمی‌آید.

**۵) اجرای فرانت‌اند (ترمینال دوم)**

```bash
cd web
npm run dev
# http://localhost:5173
```

Vite مسیر `/api` را به `http://localhost:5192` پروکسی می‌کند، پس در توسعه نیازی به تنظیم CORS نیست.

**۶) جادوی راه‌اندازی اولیه در `/setup`**

در اولین بازدید، صفحه ورود خودکار به `/setup` می‌رود. نام سازمان و یک مدیر سامانه با رمز (حداقل ۸ نویسه) بسازید:

```
http://localhost:5173/setup
```

این فرم **یک‌بارمصرف** است: اگر حتی یک کاربر در پایگاه وجود داشته باشد، `/api/setup` با خطای ۴۰۹ «راه‌اندازی اولیه قبلاً انجام شده است.» پاسخ می‌دهد و صفحه ورود دیگر به آنجا ریدیرکت نمی‌کند. مدیری که اینجا ساخته می‌شود ستون `IsLocalAdmin = 1` می‌گیرد، یعنی مجوز `*` (همه ۴۱ کد) به‌علاوه نقش `Administrator` — تنها حسابی که تب «تنظیمات» و بخش کامل امنیت را می‌بیند.

**۷) داده نمایشی (اختیاری، ولی برای دیدن برنامه توصیه می‌شود)**

بدون داده، داشبورد و تایم‌لاین خالی‌اند. بخش [داده نمونه و حساب‌های نمایشی](#داده‌نمونه‌و‌حساب‌های‌نمایشی) روش کاملش را با رمز هش‌شده و پارامتر `CleanMode` توضیح می‌دهد.

**۸) ورود**

با همان مدیری که در `/setup` ساختید وارد شوید (تب «ورود محلی»). اگر داده نمونه را بارگذاری کرده‌اید، هش حساب‌های `demo.*` را هم دارید. از اینجا:

| اگر می‌خواهید… | بروید به | نیازمند |
|---|---|---|
| مأموریت ثبت و تا تأیید پیش ببرید | `/missions` → «مأموریت جدید» | `missions.create`، `missions.approve` |
| تایم‌لاین را با زوم تست کنید | `/timeline` | `missions.view` |
| گزارش بگیرید و Excel/PDF دانلود کنید | `/reports` | `reports.view` |
| نقش و مجوز و نشست بسازید | `/security` | `security.audit.view`، `security.sessions.view` |
| قواعد مأموریت، لوگو و قالب حکم را عوض کنید | `/settings` | `settings.system.manage` (در UI فقط مدیر محلی؛ سمت سرور فعلاً چک نمی‌شود) |

## راه‌اندازی‌پایگاه‌داده

> **اصل مهم:** هیچ رمز عبوری داخل مخزن نگهداری نمی‌شود. اطلاعات اتصال فقط در فایل‌های env بیرون از مخزن (`C:\Users\<you>\.novafleet\`) و از طریق متغیرهای محیطی وارد فرآیند می‌شوند. `scripts/provision-db.sql` تنها از متغیرهای sqlcmd استفاده می‌کند و به‌تنهایی بی‌خطر است.

**۱) فایل‌های env** (یک‌بار، دستی):

`~/.novafleet/db.env` — فقط برای اسکریپت راه‌اندازی:

```
SA_USER=sa
SA_PASSWORD=<رمز sa>
SQL_HOST=<IP یا نام سرور>
DB_NAME=NovaFleetDb
APP_LOGIN=novafleet_app
APP_PASSWORD=<رمز لاگین برنامه>
```

`~/.novafleet/app.env` — برای اجرای اپلیکیشن (متغیرهای `Directory__*` هم همین‌جا می‌آیند تا نیازی به نوشتن تنظیمات دامنه در `appsettings.json` نباشد):

```
SQL_HOST=<IP یا نام سرور>
DB_NAME=NovaFleetDb
APP_LOGIN=novafleet_app
APP_PASSWORD=<رمز لاگین برنامه>
Directory__Enabled=true
Directory__Host=<dc.domain.local>
Directory__Port=389
Directory__UseSsl=false
Directory__Domain=<Domain.Local>
Directory__BaseDn=DC=domain,DC=local
```

`~/.novafleet/ldap.env` — فقط برای تست دستی مسیر دامنه؛ هیچ‌گاه به مخزن یا لاگ راه ندارد:

```
LDAP_HOST=…
LDAP_PORT=…
LDAP_SSL=…
LDAP_DOMAIN=…
LDAP_USERNAME=…
LDAP_PASSWORD=…
```

**۲) ساخت پایگاه داده:**

```bash
set -a; . "$HOME/.novafleet/db.env"; set +a
sqlcmd -S "$SQL_HOST" -U "$SA_USER" -P "$SA_PASSWORD" \
  -i scripts/provision-db.sql \
  -v DbName="$DB_NAME" -v AppLogin="$APP_LOGIN" -v AppPassword="$APP_PASSWORD"
```

اسکریپت، پایگاه داده، لاگین سطح‌سرور، کاربر دیتابیس و عضویت `db_owner` روی **همان پایگاه** را می‌سازد (EF Core در استارت‌اپ مهاجرت می‌کند و به DDL نیاز دارد). اجرای دوباره بی‌خطر است: هر چیزی را تنها در صورت نبود می‌سازد. خروجی موفق، سطر `ready` است.

**۳) جدول‌ها:** مهاجرت EF Core به‌صورت خودکار در استارت‌اپ اعمال می‌شود؛ در اولین اجرا صفحه `/setup` ساخت اولین مدیر سامانه و بذرگذاری نقش‌ها، قالب‌های پیامک و دلایل تفکیک را انجام می‌دهد.

## داده‌نمونه‌و‌حساب‌های‌نمایشی

`scripts/seed-demo.sql` پایگاه را به یک محیط نمایشی کامل تبدیل می‌کند تا داشبورد، خط زمانی، گزارش‌ها و صف پیامک با داده واقعی به‌نظر برسند. این اسکریپت **بدون رمز** است؛ هش رمز حساب‌های نمونه به‌صورت متغیر sqlcmd از بیرون مخزن داده می‌شود.

**۱) ساخت هش رمز** (یک‌بار، بیرون از مخزن). رمز نمایشی همه حساب‌های `demo.*` این است:

```
Demo@1405!
```

هش را با الگوریتم خود سامانه (PBKDF2-SHA256، ۲۱۰٬۰۰۰ تکرار، ۱۶ بایت نمک تصادفی، ۳۲ بایت کلید — همان `Pbkdf2PasswordHasher`) بسازید و در فایلی بیرون از مخزن نگه دارید — مثال `C:\Users\<you>\.novafleet\mkhash.ps1`:

```powershell
$password = 'Demo@1405!'
$salt = [byte[]](1..16 | ForEach-Object { Get-Random -Maximum 256 })
$key  = [System.Security.Cryptography.Rfc2898DeriveBytes]::Pbkdf2(
          $password, $salt, 210000,
          [System.Security.Cryptography.HashAlgorithmName]::SHA256, 32)
'pbkdf2-sha256$210000$' + [Convert]::ToBase64String($salt) + '$' + [Convert]::ToBase64String($key) |
  Set-Content "$HOME\.novafleet\demo-hash.txt" -NoNewline -Encoding ascii
```

**۲) اجرا.** چون مسیر فایل در ویندوز باید با بک‌اسلش و خارج از زنجیره اسرار باشد، یک پوشش موقت بسازید (`C:\Users\<you>\.novafleet\seed-run.sql`):

```sql
:setvar DemoPasswordHash "<محتوای demo-hash.txt>"
:r C:\Users\<you>\Documents\...\scripts\seed-demo.sql
```

```bash
set -a; . "$HOME/.novafleet/db.env"; set +a
sqlcmd -S "$SQL_HOST" -U "$SA_USER" -P "$SA_PASSWORD" -d "$DB_NAME" \
  -f 65001 -b -i "C:\\Users\\<you>\\.novafleet\\seed-run.sql" -v CleanMode=1
```

| پارامتر | معنا |
|---|---|
| `CleanMode=1` | پیش از بارگذاری، **همه مأموریت‌ها**، درخواست‌های تغییر و صف پیامک پاک می‌شوند و رکوردهای نمونه قبلی (با پیش‌شونده `D0DE00…`) حذف می‌گردند |
| `CleanMode=0` | بارگذاری تنها؛ اگر بذر قبلاً خورده باشد، اسکریپت بدون تغییر خارج می‌شود |
| `-f 65001` | ورودی UTF-8؛ بدون آن متن فارسی خراب می‌شود |

**۳) چه داده‌ای ساخته می‌شود:**

| مجموعه | مقدار | نکته |
|---|---|---|
| رانندگان | ۳۱ نفر | هر راننده فعال خودروی اختصاصی هم‌شماره دارد؛ وضعیت استخدام، بایگانی و تلفن نمونه. فهرست پیش‌فرض `/api/drivers` بایگانی‌شده را نشان نمی‌دهد (۳۰ سطر) مگر `includeArchived=true` |
| خودروها | ۳۶ دستگاه | شامل تعمیرگاه/خارج از سرویس/بایگانی‌شده برای سنجش کارت‌های وضعیت ناوگان؛ فهرست پیش‌فرض ۳۵ سطر می‌دهد و یکی بایگانی است |
| مأموریت | ۵۵۱ مأموریت | طول از **۱ ساعت تا چند روز** (۶۰ تا ۵٬۷۰۰ دقیقه) |
| پخش زمانی | ۵۹ روز قبل تا ۶۰ روز بعد | بازه تصادفی **دو ماه قبل تا دو ماه آینده** نسبت به روز اجرا |
| توزیع وضعیت | ۲۱ در انتظار بررسی، ۱۰ در حال بررسی، ۲۶۳ تأییدشده، ۱۷ در حال اجرا، ۱۴۸ انجام‌شده، ۳۲ در انتظار انصراف، ۲۹ لغو، ۳۱ رد | همه وضعیت‌های چرخه عمر قابل مشاهده‌اند |
| درخواست تغییر | ۴۰ مورد | نزدیک‌ترین مأموریت‌ها به زمان اجرا، تا در داشبورد جلوه کنند |
| صف پیامک | ۱۲۰ مورد | با وضعیت‌های ارسال/تحویل/تلاش مجدد |
| واحدهای سازمانی و مقاصد | مجموعه نمونه | برای فیلترها و تأیید مقصد |
| تنظیم | `missions.future-request-days = 90` | تا مأموریت‌های دو ماه آینده در ویرایش رد نشوند |

**۴) قواعدی که داده نمونه رعایت کرده است** — همین قواعدی که خود سامانه تحمیل می‌کند:

- **هیچ راننده‌ای دو مأموریت هم‌پوشان ندارد**؛ برای هر راننده فعال یک «خط زمانه» از دو ماه قبل راه می‌افتد و مأموریت‌ها پشت هم، با فاصله بیکاری ۴۰ تا ۱۶۰ دقیقه، می‌چیند. بین خودروهای اختصاصی هم تداخلی نیست (تأیید با کوئری `LAG` روی `Missions`؛ خروجی `driverOverlaps = 0` و `vehicleOverlaps = 0`).
- **زمان‌ها فقط ساعت کامل به وقت تهران هستند** (`Mission.ValidateHour`)؛ بنابراین دقیقه UTC همه رکوردها `:30` است.
- **هیچ برچسب زمانی آینده ندارد**: `CreatedAtUtc`، `UpdatedAtUtc` و زمان بررسی/تأیید/تقسیم همگی پیش از لحظه اجرا محدود می‌شوند.
- **کیلومترشمار نزولی نیست**؛ مسافت هر مأموریت از تابع خطی زمان محاسبه می‌شود.
- شمارنده شماره مأموریت (`MissionNumberSequences`) با آخرین شماره هم‌گام می‌شود تا شماره‌گذاری دستی بعداً تکراری نشود.

**۵) حساب‌های نمایشی.** رمز همه این‌ها `Demo@1405!` است (فقط حساب‌های `demo.*`؛ حساب مدیر که در `/setup` ساختید و حساب دامنه، رمز خود شما را دارند و هیچ‌جا ثبت نمی‌شوند):

| نام کاربری | نقش | دسترسی اصلی |
|---|---|---|
| `demo.operator1` (سمیرا کاظمی) | اپراتور | ثبت، بررسی، تأیید و تخصیص مأموریت |
| `demo.operator2` (پیمان نوروزی) | اپراتور | همان مسیر، برای تست همزمانی دو اپراتور |
| `demo.manager1` (حمید موسوی) | مدیر ناوگان | کل ناوگان + گزارش‌ها + پیامک + تنظیمات عملیاتی |
| `demo.manager2` (نگار رحیمی) | مدیر ناوگان | دوم، برای مقایسه سطوح دسترسی |
| `demo.requester1` (مریم هاشمی) | درخواست‌کننده | فقط مأموریت‌های خودش |
| `demo.requester2` (احمد بهرامی) | درخواست‌کننده | همان سطح، کاربر دوم |
| `demo.requester3` (الهام زارعی) | درخواست‌کننده | همان سطح، کاربر سوم |
| `demo.viewer1` (فرید سلطانی) | ناظر | فقط مشاهده و گزارش |

ورود: `POST /api/auth/login-local` با `{ "username": "demo.manager1", "password": "Demo@1405!" }` یا فرم صفحه ورود، تب «ورود محلی».

**چرا با حساب‌های demo تب «تنظیمات» یا بخش کامل امنیت را نمی‌بینم؟** چون هیچ‌یک از آن‌ها `IsLocalAdmin` نیستند و نقش‌های seed شده مجوز `settings.system.manage` ندارند. منو بر پایه مجوز ساخته می‌شود، پس تب مخفی است. توجه: این **محدودیت رابط کاربری** است، نه دروازه‌بانی سمت سرور — در وضعیت فعلی، `/api/settings` و `/api/audit` و `/api/users` با هر نشست معتبری پاسخ می‌دهند (بخش [محدودیت‌های شناخته‌شده](#محدودیت‌های‌شناخته‌شده) را ببینید). برای دسترسی نمایشیِ کامل‌تر، از صفحه امنیت نقش «مدیر سامانه» را به کاربر اضافه کنید یا مجوز `settings.system.manage` را مستقیم Grant کنید.

برای خروج کامل از داده نمونه، پاک‌کردن جداول با همان پیش‌شونده‌های `D0DE00…` در بخش اول اسکریپت آمده است.

## پیکربندی

مقادیر پیش‌فرض در `src/NovaFleet.Api/appsettings.json` بی‌خطرند و هیچ رمزی ندارند:

```json
{
  "ConnectionStrings": { "Default": "" },
  "Directory": { "Enabled": false, "Host": "", "Port": 636, "UseSsl": true, "Domain": "", "BaseDn": "" },
  "Sms": { "Mode": "Simulation" },
  "Cors": { "AllowedOrigins": [] }
}
```

**رشته اتصال** به یکی از سه شکل (به همین اولویت، طبق `ResolveConnectionString` در `Program.cs`):

1. `ConnectionStrings:Default` در `appsettings.json` (یا `appsettings.Development.json` و `NOVAFLEET_ConnectionStrings__Default`، چون متغیرهای محیطی با پیشوند `NOVAFLEET_` به همان کلیدها نگاشت می‌شوند)
2. متغیرهای جداگانه `SQL_HOST` / `DB_NAME` / `APP_LOGIN` / `APP_PASSWORD` — توصیه‌شده؛ اگر `Default` خالی باشد رشته اتصال از این چهارتا ساخته می‌شود، با `TrustServerCertificate=True`
3. هیچ‌کدام تنظیم نشده ⇒ اپ با پیام «رشته اتصال تنظیم نشده است؛ …» بالا نمی‌آید

برای دستورات `dotnet ef` مسیر متفاوت است: `DesignTimeDbContextFactory` فقط متغیر `NOVAFLEET_CONNECTION_STRING` را می‌پذیرد و `ConnectionStrings:Default` را از فایل config نمی‌خواند.

اگر هیچ‌کدام تنظیم نشده باشد، اپ با پیام روشن بالا نمی‌آید: «رشته اتصال تنظیم نشده است؛ …».

**متغیرهای دیگر:**

| متغیر | مصرف |
|---|---|
| `ASPNETCORE_URLS` | آدرس گوش‌دادن API (پیش‌فرض توسعه: `http://localhost:5192`) |
| `ASPNETCORE_ENVIRONMENT` | `Development` برای فرانت‌دِو |
| `Cors:AllowedOrigins` | در تولید، آدرس دقیق فرانت‌اند (کوکی + CSRF) |

دو ترمینال لازم است.

dotnet run --project src/NovaFleet.Api
# http://localhost:5192
```

**۲) فرانت‌اند:**

cd web

# http://localhost:5173
```

Vite مسیر `/api` را به `http://localhost:5192` پروکسی می‌کند، پس نیازی به تنظیم CORS در توسعه نیست. بعد از اولین اجرا، وارد صفحه `/setup` شوید و مدیر سامانه را بسازید.

## نصب‌و‌اجرا‌در‌محیط‌عملیاتی

```bash
cd web && npm run build          # خروجی: web/dist  (tsc -b && vite build)
cp -r dist ../src/NovaFleet.Api/wwwroot   # پیش از publish
dotnet publish src/NovaFleet.Api -c Release -o ./publish
```

`Program.cs` تنها در صورتی از فرانت‌اند سرو می‌کند که پوشه `wwwroot` کنار API وجود داشته باشد؛ در آن حالت `UseDefaultFiles` + `UseStaticFiles` + `MapFallbackToFile("index.html")` فعال می‌شود و **یک‌دامنه‌ای** کار می‌کند: API و UI روی یک پورت، بدون نیاز به CORS. برای جداسازی، `Cors:AllowedOrigins` را روی آدرس دقیق فرانت‌اند تنظیم کنید.

سپس `publish/NovaFleet.Api.exe` را به‌عنوان سرویس ویندوز یا زیر IIS اجرا کنید. اگر API و فرانت‌اند جداگانه مستقر می‌شوند، هر دو باید پشت HTTPS و زیر یک دامنه باشند تا کوکی نشست و هدر CSRF درست کار کنند.

## مدل‌امنیتی

- **احراز هویت:** محلی (PBKDF2-SHA256، ۲۱۰٬۰۰۰ تکرار، نمک ۱۶ بایت، کلید ۳۲ بایت) یا LDAP؛ هر دو پس از موفقیت یک نشست در پایگاه داده باز می‌کنند و پایان/خاتمه اجباری آن‌ها از صفحه امنیت ممکن است. تغییر رمز از `POST /api/auth/change-password` (حداقل ۸ نویسه) و برای کاربران دامنه مسدود است.
- **تلاش ناموفق:** هر ورود ناموفق یک `UserSession` با وضعیت Failed و یک سطر دفتر رویداد با دلیل («رمز یا نام کاربری نادرست»، «حساب غیرفعال است»، «حساب در گروه‌های مجاز نیست») ثبت می‌کند، بدون قفل کردن حساب — اگر قفل پس از N تلاش ناموفق لازم است، باید اضافه شود.
- **CSRF:** همه فراخوانی‌های تغییردهنده `/api` باید هدر `X-Requested-With: XMLHttpRequest` داشته باشند (مسیرهای `/api/auth` و `/api/setup` مستثنا).
- **مجوزها:** `PermissionCatalog` چهل‌ویک کد دارد: یک کد `*` (همه دسترسی‌ها)، سه کد گروه مانند `missions.*` / `drivers.*` / `vehicles.*` و ۳۷ کد دانه‌درشت (`missions.approve`، `missions.print`، `notifications.sms.templates.manage`، `security.sessions.view`، `settings.system.manage` …). نقش‌های پیش‌فرض: مدیر سامانه، مدیر ناوگان، اپراتور، درخواست‌کننده، ناظر. هر کاربر می‌تواند علاوه بر نقش، مجوز مستقیم (Grant/Deny) داشته باشد و نگاشت گروه دایرکتوری هم نقش اضافه می‌کند. منوی فرانت‌اند بر پایه همین کدها ساخته می‌شود، پس تبی که مجوزش را ندارید نمایش داده نمی‌شود.
- **سطح‌دسترسی داده:** درخواست‌کننده فقط مأموریت‌های خودش را می‌بیند؛ مدیر ناوگان و اپراتور کل محدوده را.
- **صف رویداد:** هر اقدام حساس با عامل، نتیجه و زمان (به وقت تهران) ثبت و قابل فیلتر است.
- **همزمانی:** ستون‌های `RowVersion` در خودرو و راننده، تغییر هم‌زمان دو اپراتور را به خطای ۴۰۹ تبدیل می‌کنند.
- **اسرار:** خارج از مخزن، فقط env؛ رمز پیامک و Bind LDAP در همین فایل‌ها.

## محدودیت‌های‌شناخته‌شده

**۱) دروازه‌بانی مجوز روی همه endpointها یکسان نیست.** الگو این است که خودِ سرویس با `currentUser.Require(...)` مجوز را می‌سنجد و روی گروه `/api` سیاست `RequireAuthorization` نگذاشته شده است. این الگو در سرویس‌های حساس رعایت شده (`MissionService`، `ReportService`، `DriverService`، `VehicleService`، `LocationService`، `OrganizationUnitService`، `TimelineService`، `DashboardService`، `NotificationService`) — برای مثال Viewer روی `POST /api/reports/missions/run` پاسخ ۴۰۳ «برای انجام این عملیات مجوز ندارید» می‌گیرد.

اما شش سرویس هیچ `Require` ندارند و **با هر نشست معتبری** کار می‌کنند:

| سرویس | endpointها | آزموده‌شده با `demo.viewer1` (۴ مجوز) |
|---|---|---|
| `SettingsService` | `GET /api/settings`، `PUT /api/settings/organization`، `mission-rules`، `session-policy`، `mission-order-template` | خواندن ۲۰۰ و نوشتن ۲۰۰ |
| `UserService` | `GET /api/users` | ۲۰۰ |
| `RoleService` | `GET /api/roles` | ۲۰۰ |
| `SessionService` | `GET /api/sessions` | ۲۰۰ |
| `AuditQueryService` | `GET /api/audit` | ۲۰۰ |
| `SmsService` | `GET /api/sms`، `GET /api/sms/templates` | ۲۰۰ |

**راه اصلاح:** افزودن `currentUser.Require(...)` در متدهای همین شش سرویس (همان کاری که `ReportService.RunAsync` می‌کند) یا نشاندن `RequireAuthorization` با policy روی endpointها. تا پیش از اصلاح، سامانه را فقط پشت شبکه داخلی و با حساب‌های مورد اعتماد اجرا کنید و انتظار نداشته باشید مخفی‌کردن تب در UI به‌تنهایی دسترسی را قطع کند.

**۲) قفل حساب پس از تلاش ناموفق وجود ندارد**؛ فقط ثبت می‌شود. **۳) آزمون نوشتہ‌شده‌ای نداریم**؛ پروژه‌های تست خالی‌اند. **۴) ارقام جدول گزارش‌ها لاتین است.** **۵) باندل فرانت‌اند code-split نشده است.**

## احراز‌هویت‌با‌active‌directory

برای فعال کردن ورود با دامنه ویندوز:

```json
"Directory": {
  "Enabled": true,
  "Host": "dc1.corp.local",
  "Port": 636,
  "UseSsl": true,
  "Domain": "Corp.Local",
  "BaseDn": "DC=corp,DC=local",
  "BindDn": "svc_fleet",
  "BindPassword": "…"
}
```

`BindDn`/`BindPassword` اختیاری‌اند؛ برای جست‌وجوی کاربران لازم‌اند. در صورت نبود آن‌ها، ورود با UPN (`user@domain`) انجام می‌شود. سپس از صفحه ورود، تب «ورود با دامنه» یا `POST /api/auth/login-ldap` استفاده کنید.

**جریان ورود با دامنه:** سامانه با UPN (`user@Domain`) روی LDAP bind می‌شود، کاربر را در `BaseDn` جست‌وجو می‌کند، در صورت نبود یک حساب «دامنه‌ای» می‌سازد، عضویت‌های گروه را در `DirectoryGroupsJson` هم‌گام می‌کند و نقش‌ها را از نگاشت‌ها استخراج می‌کند. اگر هیچ نقشی به کاربر نرسد، دسترسی **رد** می‌شود (۴۰۳ «حساب شما در گروه‌های مجاز سامانه نیست») — یعنی bind موفق، ولی دسترسی نه.

**نگاشت گروه به نقش:** از صفحه امنیت یا `POST /api/roles/directory-mappings` با `groupName` و `roleId`. مقدار `groupName` می‌تواند کل DN یا فقط `CN` گروه باشد (مقایسه بی‌حساس به بزرگی/کوچکی حروف و بدون فاصله اضافه):

```json
{ "groupName": "تیم برنامه نویسی", "roleId": "…" }
```

**بارگذاری تنظیمات بدون قرار دادن مقدار در مخزن:** به‌جای ویرایش `appsettings.json`، از متغیرهای محیطی با جداکننده دو‌زیره استفاده کنید (همین کلیدها در `~/.novafleet/app.env` نگه داشته می‌شوند):

```bash
Directory__Enabled=true
Directory__Host=corp.local
Directory__Port=389
Directory__UseSsl=false
Directory__Domain=Corp.Local
Directory__BaseDn=DC=corp,DC=local
```

**LDAPS:** در حالت امن، `Port=636` و `UseSsl=true` با اعتبارسنجی کامل گواهی سرور؛ این مسیر مستلزم آن است که DC واقعاً گواهی LDAPS نصب‌شده داشته باشد و نام سرور با `Subject` گواهی بخواند. اگر handshake برقرار نشود، اتصال با پیام «ارتباط با سرویس دایرکتوری برقرار نشد» رد می‌شود و باید یا گواهی DC کامل شود یا موقتاً LDAP ساده روی ۳۸۹ استفاده شود.

> مسیر دامنه در این نصب با LDAP ساده روی پورت ۳۸۹ و نگاشت گروه «تیم برنامه نویسی» → نقش «مدیر ناوگان» آزمایش و تأیید شده است: ورود از رابط کاربری، ساخت خودکار کاربر، دریافت ۲۵ مجوز مؤثر و ثبت نشست و رویدادها در دفتر امنیت.

## پیامک‌شبیه‌سازی‌و‌درگاه‌واقعی

`Sms:Mode` دو مقدار می‌پذیرد:

| حالت | رفتار |
|---|---|
| `Simulation` (پیش‌فرض) | پیامک در صف ثبت و پس از چند لحظه «تحویل‌شده» می‌شود؛ بدون تماس بیرونی |
| `Adp` | ارسال واقعی به درگاه ADP (SOAP) با `Endpoint`، `Username`، `Password` و `SenderNumber` |

```json
"Sms": {
  "Mode": "Adp",
  "Endpoint": "https://sms.example/SmsService.asmx",
  "Username": "…",
  "Password": "…",
  "SenderNumber": "…",
  "TimeoutSeconds": 20
}
```

اگر `Mode = Adp` ولی `Endpoint` خالی باشد، سامانه به‌طور خودکار به شبیه‌سازی برمی‌گردد. `SmsQueueWorker` ارسال، تلاش مجدد و خواندن وضعیت تحویل را مدیریت می‌کند؛ از صفحه پیامک هم می‌توان دستی تلاش مجدد کرد یا با دکمه «تست» یک پیامک نمونه فرستاد. قالب‌ها برای هر رویداد (تأیید، تغییر، انصراف و …) قابل ویرایش‌اند و توکن‌های جلالی در آن‌ها هنگام ارسال تبدیل می‌شوند.

## چرخه‌عمر‌مأموریت

```
۱ در انتظار بررسی
  → شروع بررسی → ۲ در حال بررسی
      → تأیید و تخصیص → ۳ تأییدشده → شروع اجرا → ۴ در حال اجرا
          → پایان / ثبت کیلومتر → ۵ انجام‌شده
          → خاتمه زودهنگام → ۵ با یادداشت
          → درخواست انصراف → ۶ در انتظار انصراف → تأیید/رد
      → رد → ۸ ردشده
  لغو (۷) از هر حالتی که به مرحله انجام/لغو/رد نرسیده باشد
```

تغییرات میانی مسیر (تمدید، تعویض راننده/خودرو، تفکیک) به‌صورت «درخواست تغییر» ثبت و جداگانه بررسی/تصمیم می‌شوند تا سوابق حفظ شود. **کنترل تداخل** همیشه بر پایه زمان برنامه‌ریزی‌شده و با در نظر گرفتن فاصله ایمنی است، نه صرف وجود یک مأموریت فعال.

## خط زمانی

`GET /api/timeline?fromUtc=&toUtc=&driverId=&vehicleId=` مأموریت‌هایی را برمی‌گرداند که با بازه درخواست هم‌پوشانی زمانی دارند (وضعیت‌های ۱، ۲، ۳، ۴، ۵ و ۶؛ لغو و ردشده عمداً نمایش داده نمی‌شوند).

نمایش در `web/src/pages/TimelinePage.tsx`:

- **یک ردیف برای هر راننده.** ردیف «بدون راننده» درخواست‌های تخصیص‌نیافته را نگه می‌دارد. اگر گزینه «فقط رانندگانی که در این بازه مأموریت دارند» خاموش باشد، رانندگان بیکار هم با برچسب «بدون مأموریت» لیست می‌شوند.
- **زوم پیوسته از یک ساعت تا دو ماه.** پنج مقیاس با پیکسل بر ساعت تعریف می‌شود: ساعت `۲۴`، روز `۲٫۷`، هفته `۱٫۰۸`، ماه `۰٫۴۵`، فصل `۰٫۱۸`. سلول‌های سرِ جدول خودکار تغییر granularity می‌دهند: در مقیاس ساعت هر خانه یک ساعت است، در روز/هفته یک روز، و در ماه/فصل یک هفته.
- **تناسب خودکار بازه با مقیاس.** با تغییر زوم، بازه حول مرکز فعلی آنقدر کوچک یا بزرگ می‌شود که عرض ریل بین ۶۲۰ تا ۶۲۰۰ پیکسل بماند؛ برای همین زوم «ساعت» روی بازه سه‌هفته‌ای، صفحه را نمی‌شکند. شش دکمه «بازه سریع» (یک روز تا دو ماه) نیز هرکدام زوم مناسب خودش را می‌چیند.
- **پر کردن عرض یا اسکرول، خودکار.** عرض ریل با `ResizeObserver` اندازه گرفته می‌شود؛ اگر جمع ستون‌ها کمتر از فضای موجود باشد همه ستون‌ها با یک ضریب یکسان بزرگ می‌شوند تا ریل تا لبه صفحه پر شود، و اگر بیشتر باشد ضریب روی ۱ می‌ماند و اسکرول افقی فعال می‌شود. ستون نام راننده (`۱۹۰px`) در مقیاس حساب نمی‌آید و نوارها، خط «اکنون» و باند ماه‌ها هم با همان ضریب مقیاس می‌خورند، پس هیچ‌وقت نوار از ریل بیرون نمی‌زند.
- **برش نوار در لبه‌های پنجره**؛ مأموریت چندروزه‌ای که نیمی‌اش بیرون بازه است، تا لبه بریده می‌شود و از ردیف بیرون نمی‌زند. عرض حداقلی ۱۰ پیکسل دارد تا مأموریت یک‌ساعته در مقیاس ماه هم کلیک‌پذیر بماند.
- **کلیک = دیدن و ویرایش.** مدال سریع، اطلاعات کامل (وضعیت، نوع، درخواست‌کننده، راننده، خودرو، زمان‌ها، مسافت) را نشان می‌دهد و اگر مأموریت در وضعیت «در انتظار بررسی» و کاربر مجوز `missions.edit` داشته باشد، عنوان/مبدأ/مقصد/تاریخ و ساعت شروع و پایان را همان‌جا با `PUT /api/missions/{id}` ذخیره می‌کند. برای وضعیت‌های دیگر مدال راهنمای «درخواست تغییر» را نشان می‌دهد و لینک «صفحه مأموریت» همیشه هست.
- **خط «اکنون»** و سایه آخر هفته‌ها (`جمعه`) روی ریل؛ برچسب روز و ماه جلالی، ساعت‌ها با ارقام فارسی.

## کارهای‌انجام‌شده‌در‌این‌نسخه

**مخزن و معماری**

- ساخت کامل راه‌حل چهارلایه `NovaFleet.sln` (Domain / Application / Infrastructure / Api) با Build بدون warning و خطا، به‌همراه پروژه‌های تست خالی `tests/NovaFleet.UnitTests` و `tests/NovaFleet.IntegrationTests`.
- پیاده‌سازی موجودیت‌ها و قواعد دامنه: مأموریت، راننده، خودرو، مقصد، واحد سازمانی، کاربر/نقش/مجوز، صف پیامک، قالب‌ها، درخواست تغییر، دفتر رویداد و تنظیمات.

**بک‌اند**

- ۹۸ endpoint (۳۴ GET، ۴۸ POST، ۱۴ PUT، ۲ DELETE) در `EndpointMapper` برای مأموریت، راننده، خودرو، مقصد، پیامک، گزارش، امنیت، تنظیمات، سازمان و تایم‌لاین.
- احراز هویت محلی + LDAP، نشست‌های کوکی‌محور با پایان اجباری، ثبت هر تلاش ناموفق در نشست و دفتر رویداد، هدر CSRF، و ۴۱ کد مجوز در `PermissionCatalog` (یک `*`، سه گروه `x.*` و ۳۷ کد دانه‌درشت) با Grant/Deny مستقیم و نگاشت گروه دایرکتوری به نقش.
- چرخه عمر کامل مأموریت: ثبت → بررسی → تأیید و تخصیص → اجرا → پایان/خاتمه زودهنگام، به‌همراه انصراف، لغو، رد، تمدید، تعویض راننده/خودرو و تفکیک؛ همه با کنترل تداخل راننده و خودرو و فاصله ایمنی قابل تنظیم.
- دو Worker پس‌زمینه: انتقال خودکار وضعیت/آزادسازی منابع، و ارسال و پیگیری تحویل پیامک با تلاش مجدد.
- خروجی: حکم مأموریت PDF راست‌به‌چپ با QuestPDF، گزارش‌های پارامتری Excel (ClosedXML) و PDF.
- تقویم جلالی سمت سرور با `PersianCalendar` و مبنای وقت تهران (+۳:۳۰)؛ دامنه فقط ساعت کامل تهران را می‌پذیرد.

**فرانت‌اند و طراحی**

- تم «Emerald Premium» (سبز زمردی/طلایی، وزیرمتن، RTL کامل، دسترس‌پذیری کیبورد و فاصله رنگ) و کتابخانه کامپوننت‌های `card/btn/input/badge/modal/…`.
- صفحه‌ها: داشبورد با نمودارهای Recharts و ارقام فارسی، لیست و جزئیات مأموریت، رانندگان، خودروها (کارت وضعیت با تفکیک آمادگی ذاتی از درگیری زمانی)، مقاصد، پیامک، گزارش‌ها، امنیت (کاربران/نقش‌ها/نشست‌ها/دفتر رویداد)، تنظیمات و خط زمانی.
- اصلاح‌های این دوره: تداخل متن کارت وضعیت خودرو با نمودار برطرف شد؛ محورهای نمودارها فارسی شدند؛ دو اشکال مشترک تبدیل تاریخ/ساعت (`toJalali` و `formatFaDateTime`) که ساعت را دوباره جابه‌جا می‌کرد اصلاح شد.
- رفع خطای ۵۰۰ در شش گزارش مأموریتی (`missions`، `missions-distance`، `driver-activity`، `vehicle-usage`، `org-unit`، `mission-status`): در `ReportService` فیلترها باید روی خودِ موجودیت `Mission` اعمال شوند و پرتاب به رکورد گزارش باید **آخرین** مرحله باشد، وگرنه EF Core نمی‌تواند `Where` را به SQL ترجمه کند و `InvalidOperationException` می‌دهد. اکنون `Filtered()` فیلترها را می‌زند و `LoadRowsAsync()` یک‌بار با join راننده/خودرو به `MissionReportRow` پرتاب می‌کند؛ گروه‌بندی‌ها روی همین فهرست در حافظه انجام می‌شود.

**داده و بررسی**

- پایگاه `NovaFleetDb` روی SQL Server ساخته شد (لاگین برنامه با `db_owner` روی همین پایگاه) و مهاجرت EF Core اعمال شد.
- `scripts/seed-demo.sql` نوشته و اجرا شد: ۳۱ راننده، ۳۶ خودرو، ۵۵۱ مأموریت با طول ۱ ساعت تا چند روز روی بازه دو ماه قبل تا دو ماه آینده، ۴۰ درخواست تغییر و ۱۲۰ پیامک — بدون هیچ هم‌پوشانی راننده یا خودرو، بدون برچسب آینده، بدون کیلومتر نزولی و با ساعت کامل تهران.
- مسیر ورود با دامنه روی LDAP ساده تست و تأیید شد (ورود، ساخت خودکار کاربر، نگاشت گروه به نقش، ثبت نشست و رویداد).
- جریان «کلیک روی نوار تایم‌لاین → مشاهده → ویرایش → ذخیره» روی API واقعی و رابط کاربری آزمایی شد (ذخیره و سپس بازگردانی مقدار).
- هر هشت گزارش با `POST /api/reports/{key}/run` روی پایگاه پر اجرا شدند و جدول با سطر برگرداندند؛ شش گزارش مأموریتی پس از اصلاح `ReportService` از ۵۰۰ به خروجی سالم رسیدند.
- بیست‌وشش تصویر از همه بخش‌ها با مرورگر واقعی (۱۶۰۰×۱۰۰۰) در `docs/screenshots/` گرفته و به همین README متصل شد.

**باقی‌مانده**

- باندل فرانت‌اند یک تکه است (~۸۶۰ کیلوبایت)؛ code-splitting با `React.lazy` ارزش انجام دارد.
- پروژه‌های تست ساختار دارند ولی هیچ آزمون نوشته‌شده‌ای ندارند؛ اولویت: قواعد تداخل، چرخه عمر و تبدیل جلالی.
- ارقام جدول گزارش‌ها با ارقام لاتین چاپ می‌شوند؛ برای یکدستی با بقیه رابط، فارسی‌کردن آن‌ها در `ReportService` باقی است.
- فایل مجوز (LICENSE) به مخزن اضافه نشده است؛ تا پیش از آن، شرایط بخش [مجوز](#مجوز) حاکم است.
