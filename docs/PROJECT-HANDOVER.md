# تحویل پروژه Nova Fleet به سیستم و دستیار بعدی

آخرین به‌روزرسانی: **۱۴۰۵/۰۸/۲۶ (۲۰۲۶-۱۱-۱۷)** — ثبت مأموریت با تاریخ گذشته پیاده‌سازی و در مرورگر آزمایش شد؛ پذیرش نهایی ماژول نگهداری همچنان باز است.

## ۱. ابتدا این بخش را بخوانید

- پروژه یک **سامانهٔ وب** است، نه WPF: .NET 10، ASP.NET Minimal API، EF Core/SQL Server، React 19، TypeScript، Vite 8، Tailwind 4، TanStack Query و Recharts.
- مخزن: `https://github.com/Shahabs2004/Nova-Fleet-Management`؛ شاخهٔ کار `main`؛ مبنای آغاز این کار `41e11d234af33df4b67b580d1ee81b1202d6a744`.
- ریشهٔ واقعی مخزن در سیستم قبلی: `D:\Projects\NovaFleet\Nova-Fleet-Management`؛ پوشهٔ والد Git نیست.
- **پیاده‌سازی اصلی نگهداری انجام شده است؛ پذیرش نهایی کامل نیست.** تیک پیاده‌سازی به معنی آزمون همهٔ حالات یا آمادگی انتشار عملیاتی نیست.
- کاربر صریحاً ادامه و تکمیل ماژول با تصاویر موقت و آزمایش روی **دیتابیس محلی جداگانه با دادهٔ ساختگی** را مجاز کرده است.
- در آخرین درخواست، کاربر خواست وضعیت فعلی و همین چک‌لیست در GitHub ثبت شود، سپس توسعه و تست ادامه یابد. برای نتیجهٔ واقعی انتقال، `git log`، `git status` و مرجع remote را بررسی کنید؛ متن سند به‌تنهایی اثبات push نیست.
- هیچ تغییر روی دیتابیس عملیاتی، ارسال پیامک واقعی، نصب وابستگی یا انتشار نصاب در این مرحله انجام نشده است؛ این موارد همچنان مجوز مستقل می‌خواهند.
- تصاویر بهتر به آینده موکول شده‌اند و مانع تکمیل عملکرد نیستند.

## ۲. قواعد ادامهٔ کار

1. این سند و [مشخصات تصاویر](maintenance-pixel-art-assets.md) را بخوانید؛ سپس وضعیت واقعی کد و Git را بررسی کنید.
2. تغییرات محلی را حفظ کنید؛ سند یا حافظه را جایگزین شواهد کد نکنید.
3. از بخش کارهای باز، یک واحد قابل آزمون بردارید؛ پس از نتیجهٔ واقعی، تیک و شواهد آن را همین‌جا ثبت کنید.
4. تصمیم‌های قطعی زیر را دوباره از کاربر نپرسید. تصمیم تازهٔ محصول را حدس نزنید.
5. **هر مرحلهٔ پیاده‌سازی و آزمون، پیش از تحویل/کامیت بعدی باید این سند را به‌روز کند.** نام تست/فرمان، نتیجه، محدودیت و قدم بعدی را ثبت کنید.
6. رمز، کوکی، کلید، bootstrap، دادهٔ واقعی و فاکتور واقعی وارد Git نشوند. clone شامل دیتابیس و اسرار سیستم قبلی نیست.
7. پیش از اجرای تست .NET در Qoder، راهنمای `run-tests` و overlay احتمالی مخزن را بررسی کنید؛ runner موجود xUnit/VSTest است.

## ۶. نکات فنی و محدودیت‌های صریح

- `PerformedAtUtc` هنوز timestamp در قرارداد و دیتابیس است؛ تغییر اخیر فقط ورودی و نمایش ساعت را حذف کرده است. DateField در حالت بدون ساعت، بخش زمان داخلی را حفظ می‌کند (ساعت/دقیقهٔ لحظهٔ باز شدن فرم، ثانیه صفر). **تبدیل backend به DateOnly انجام نشده** و لازم نیست. **بررسی اثر زمان پنهان انجام شد (۱۴۰۵/۰۸/۲۶):** دو سرویس در یک روز با کیلومتر صعودی ولی timestamp یکسان (برخورد ساعت/دقیقه) قبلاً به‌اشتباه «تعارض هم‌زمان» تشخیص داده و رد می‌شدند. رفع در `OdometerLedger.Conflicts`: differing km در یک timestamp فقط وقتی تعارض است که یک قرائت غیرسرویس (زمان واقعی) در گروه باشد؛ قرائت‌های سرویس (`SourceKind=="maintenance`) پیشرفت کیلومتری محسوب می‌شوند. تشخیص عقب‌گرد بین timestampهای متفاوت دست‌نخورده است. نمایش دفترچه برای timestamp یکسان با `ThenByDescending(Kilometers)` پایدار شد. شواهد: تست‌های `SameDayServicesWithIncreasingMileageAreNotFalseConflicts` (قبلاً FAIL با ValidationAppException، اکنون PASS) و `SameDayServiceBelowEarlierReadingStillFlagsBackwardsConflict` (PASS)؛ کل تست واحد **۳۱۶ Passed / ۰ Failed / ۰ Skipped**. محدودیت باقی‌مانده: دو سرویس هم‌روز با کیلومتر متفاوت دیگر «تعارض» علامت نمی‌خورند (مطابق تصمیم «ساعت سرویس اهمیت ندارد»)؛ خطای ورودی کیلومتر پایین‌تر در همان روز فقط اگر نسبت به روز قبل عقب‌گرد باشد تشخیص داده می‌شود.
- آخرین معیار دفترچه از شمارش تعارض به مجموعهٔ شناسه‌ها + شدت اختلاف تبدیل شده؛ تست اصلاح تدریجی و منع بدترشدن نوشته و سبز شد.
- ذخیرهٔ همگامِ تغییر کیلومتر در DbContext ممنوع شده تا مسیر ledger دور زده نشود؛ مسیر async با تراکنش و قفل مرتب‌شدهٔ خودرو کار می‌کند.
- در اصلاح مراجعه، ترتیب افزودن child مهم است: ابتدا `record.Items.Add(entity)` سپس `db.MaintenanceRecordItems.Add(entity)`؛ معکوس آن relationship fixup را دوباره وارد collection می‌کند و حذف Add باعث Modified شناخته‌شدن شناسهٔ جدید می‌شود.
- SQLite رفتار همهٔ concurrency tokenها و قفل SQL را اثبات نمی‌کند.
- نقش‌های قبلاً تنظیم‌شده خودکار مجوز جدید نمی‌گیرند. مدیر محلی باید از مدیریت دسترسی، مجوزهای نگهداری را آگاهانه به نقش‌ها بدهد؛ Deny و تنظیم موجود بازنویسی نشود.
- الگوی سرویس پیش‌فرض تولیدی seed نشده؛ مدیر از رابط الگو می‌سازد. داده‌های نمونه فقط در DB آزمایشی‌اند و توصیهٔ فنی سرویس خودرو نیستند.
- تب قطعات سابقهٔ مصرف/تعویض و ضمانت است؛ موجودی یا مدل مستقل «قطعات نصب‌شدهٔ اولیه» پیاده نشده و وضعیت قبلی ناشناخته معرفی می‌شود.
- **بازبینی امنیت پیوست/ورودی/خطا انجام شد (۱۴۰۵/۰۸/۲۶):** پیوست با امضای ابتدایی (PNG/JPEG/PDF) + تطابق پسوند بررسی می‌شود، نه تحلیل کامل فایل؛ نام فایل با `Path.GetFileName` پس از نرمال‌سازی جداکننده‌ها از path traversal پاک می‌شود، نویسه‌های کنترلی رد و طول ≤۲۰۰ محدود می‌شود؛ mime شناسایی‌شده (نه ارسالی کاربر) ذخیره می‌شود؛ دانلود همیشه `application/octet-stream` + nosniff + CSP sandbox + no-store + Content-Disposition attachment است (حتی با mime تصویر، رندر inline نمی‌شود). مالکیت record/vehicle، منع پیوست به سابقهٔ باطل‌شده و سقف ۲۰ با تراکنش Serializable + قفل خودرو enforced. ورودی‌ها (جست‌وجو، بازهٔ گزارش، km، مبلغ، نام‌ها) اعتبارسنجی و EF parameterized هستند (بدون SQL injection). خطاها: `ApiExceptionHandlerMiddleware` اولین middleware است و همهٔ استثناها را به پیام فارسی امن نگاشت می‌کند؛ `DbUpdateException` خام → ۵۰۰ عمومی بدون نشت پیام/جزئیات SQL؛ `DbUpdateConcurrencyException` → ۴۰۹؛ هیچ `UseDeveloperExceptionPage` وجود ندارد (حتی در Development stack trace نشت نمی‌کند)؛ OpenAPI/Scalar فقط Development؛ کوکی HttpOnly/SameSite=Strict/Secure. شواهد: ۳ تست واحد پیوست (`AttachmentValidationRejectsOversizeDisguisedAndMismatchedFiles` شامل oversize/undersize/MZ disguised/mismatch/truncated JPEG-PDF/control-char/traversal، `AttachmentCountIsCappedAtTwenty`، `AttachmentRejectedOnVoidedRecord`) و ۴ تست middleware (no-leak 500، concurrency 409، نگاشت 401/403/404/409، BadHttpRequest 400)؛ کل واحد **۳۲۲ سبز**، middleware **۸ سبز**. محدودیت: آزمون HTTP واقعی multipart (فرم ناقص/بیش‌ازحد در سطح endpoint) نیازمند API در حال اجرا روی DB مجزا است و به گذر مرورگری/Integration موکول شد.
- خطای multipart نامعتبر به پیام فارسی ۴۰۰ نگاشت شد (InvalidDataException/IOException بدون بلعیدن لغو درخواست). **رقابت نام تکراری الگو رفع شد (۱۴۰۵/۰۸/۲۶):** `SaveTemplateAsync` پیش‌بررسی نام دارد ولی تراکنش/قفل ندارد (الگو سراسری است)؛ دو ذخیرهٔ هم‌زمان می‌توانستند از بررسی عبور کنند و شاخص یکتای `Name` بازنده را با `DbUpdateException` رد کند → ۵۰۰. اکنون `SaveChangesAsync` در try/catch است: در `DbUpdateException` (به‌جز `DbUpdateConcurrencyException` که همچنان ۴۰۹ می‌شود) دوباره بررسی می‌کند آیا نام گرفته شده؛ اگر بله `ValidationAppException` فارسی «الگویی با این نام وجود دارد.» (۴۰۰) و در غیر این صورت خطای اصلی بازپرتاب می‌شود. برنامه‌ها به‌دلیل تراکنش Serializable + قفل خودرو از قبل در برابر رقابت نوع تکراری محافظت‌اند. شواهد: تست واحد `DuplicateTemplateNameIsRejectedOnCreateAndRename` (ایجاد و تغییرنام به نام موجود → ۴۰۰)؛ کل واحد **۳۱۷ Passed / ۰ Failed / ۰ Skipped**. تست رقابت واقعی `ConcurrentDuplicateTemplateNameSurfacesValidationNotServerError` (۴ ایجاد هم‌نام → دقیقاً یک موفق و سه ۴۰۰) نوشته و کامپایل شد؛ اجرا نیازمند SQL Server مجزای localhost است (محدودیت محیط در بخش ۸).
- نام‌های بلند بدون فاصله (مثل model ساختهٔ تست‌های SQL) از کارت‌های ناوگان بیرون می‌زد؛ با `overflow-wrap: anywhere` روی `m-panel` و `min-width: 0` روی فرزندان `m-row`/`m-header` برطرف شد. خودروهای «آزمون همزمانی …» دادهٔ ساختگی تست SQL در DB آزمایشی‌اند.
- **کوئری ناوگان محدود شد (۱۴۰۵/۰۸/۲۶):** شاخهٔ فیلتردار `FleetAsync` قبلاً همهٔ خودروهای منطبق را می‌خواند و `BuildVehiclesAsync` تاریخچهٔ کامل قرائت/سوابق همه را یک‌جا بار می‌کرد. اکنون ارزیابی در دسته‌های ۵۰تایی (`candidates.Chunk(50)`) انجام می‌شود تا اوج حافظه و اندازهٔ هر کوئری به یک دسته محدود شود؛ predicate، ترتیب (Brand سپس Id) و منطق تعارض دست‌نخورده‌اند. شاخهٔ بدون فیلتر از قبل در DB صفحه‌بندی می‌شود. سابقهٔ سرویس در UI با `useInfiniteQuery` (pageSize=50) افزایشی است. **دفترچهٔ کیلومتر عمداً تاریخچهٔ کامل را نگه می‌دارد:** تشخیص تعارض در سرور به همهٔ قرائت‌های همان خودرو نیاز دارد، فهرست قرائت‌ها فقط در جدول دفترچهٔ همان خودرو مصرف می‌شود (جاده از records استفاده می‌کند نه قرائت‌ها)، و حجم آن به یک خودرو محدود است؛ صفحه‌بندی نمایشی بار سرور را کم نمی‌کند و به‌عنوان بهبود UX آینده موکول شد. شواهد: تست‌های `FleetUnknownFilterPaginatesAcrossEvaluationBatches` (۵۱ خودرو فراتر از دستهٔ ۵۰؛ totalCount/page بدون حذف/تکرار) و `FleetStateFilterSeparatesDueHealthyAndUnknown`؛ کل واحد **۳۱۹ Passed / ۰ Failed / ۰ Skipped**.
- UI تقسیم مأموریت از قبل وجود نداشت؛ قرارداد API تقسیم اصلاح شده، نه یک فرم جدید تقسیم.
- build وب هشدار اندازهٔ bundle دارد؛ به‌تنهایی شکست آزمون نیست.
