# راهنمای یکپارچه‌سازی سامانه پیامک آتیه داده‌پرداز (payamSMS) — درگاه REST

این سند قرارداد درگاه **REST** (حالت `Api`) را ثبت می‌کند؛ مکملِ
[payam-sms-soap-v2.md](payam-sms-soap-v2.md) برای حالت `Wsdl`. هدف این است که مراجعات بعدی
نیازی به کاوش دوباره نداشته باشند و بدانند کدام بخش قرارداد **تأییدشده** و کدام بخش **استنباطی** است.

| مورد | مقدار |
|---|---|
| سرویس‌دهنده | آتیه داده‌پرداز (payamSMS) — همان سرویس‌دهنده حالت Wsdl |
| آدرس نقطه اتصال REST | `https://www.payamsms.com/services/rest/index.php` |
| روش | `POST` با بدنه JSON و `Content-Type: application/json` |
| مرجع قرارداد | پروسیجر `SP_SendSMS` (پایگاه `model`) + فراخوان‌های فقط‌خواندنی روی سرویس زنده |
| تاریخ کاوش زنده | ۱۴۰۵/۰۸/۲۳ (2026-11-14) |
| پیاده‌سازی | [src/NovaFleet.Infrastructure/Sms/PayamSmsRestGateway.cs](../../src/NovaFleet.Infrastructure/Sms/PayamSmsRestGateway.cs) |

> **قانون منبع‌خوانی:** بخش‌های ۱ و ۲ عینِ قرارداد مشاهده‌شده‌اند (تأییدشده). بخش ۳ شکل پاسخ موفقِ
> `send` را که هنوز با پاسخ زنده دیده نشده، از قرارداد SOAP وام گرفته و **استنباطی** علامت زده است.
> هر جا پاسخ زنده در دسترس باشد، بر استنباط اولویت دارد.

## ۱. ساختار درخواست (تأییدشده)

همه درخواست‌ها یک شیء JSON با سه کلید احراز هویت و یک `method` هستند. برخلاف SOAP، خبری از
envelope و SOAPAction نیست؛ خودِ `method` عملیات را انتخاب می‌کند.

```json
{
  "organization": "…",
  "username": "…",
  "password": "…",
  "method": "send",
  "messages": [
    { "sender": "9820003775", "recipient": "989121112233", "body": "متن پیام", "customerId": 1 }
  ]
}
```

| کلید | نوع | شرح |
|---|---|---|
| `organization` | string | نام سازمان/خوشه سرویس‌دهنده |
| `username` | string | شناسه کاربری |
| `password` | string | کلمه عبور جاری |
| `method` | string | نام عملیات (`send`، `getbalance`، …) |
| `messages` | array | فقط برای `send`؛ آرایه پیام‌ها |

کلیدهای هر پیام در `messages`:

| کلید | نوع | شرح |
|---|---|---|
| `sender` | string | شماره فرستنده اختصاصی، مانند `9820003775` |
| `recipient` | string | شماره گیرنده با کد کشور، حداکثر ۱۲ رقم (`98912…`) |
| `body` | string | متن پیام (فارسی/لاتین، UTF-8 خام) |
| `customerId` | number | شناسه مشتری؛ در پروسیجر مرجع ثابت `1` است |

نکته‌ها:
- `customerId` در پروسیجر مرجع `SP_SendSMS` به‌صورت ثابت `1` مقداردهی شده و همین پیاده‌سازی
  نیز همان را می‌فرستد (`PayamSmsRestGateway.CustomerId`).
- شماره گیرنده باید مثل حالت Wsdl به قالب کد کشور نرمال شود؛ همان تابع
  `PayamSmsGateway.NormalizeDestination` دوباره استفاده می‌شود (`0912…` → `98912…`).

## ۲. ساختار پاسخ و متدهای کشف‌شده (تأییدشده)

پاسخ همیشه یک پوشش JSON است:

```json
{ "code": 200, "message": "send result", "data": … }
```

| `code` | معنی | رفتار پیاده‌سازی |
|---|---|---|
| `200` | درخواست پردازش شد؛ نتیجه واقعی داخل `data` است | `data` تفسیر می‌شود |
| `111` | نام متد/پارامتر نامعتبر (`check parameters {method}`) | خطای **دائمی** — تلاش دوباره فایده ندارد |
| سایر | پاسخ ناموفق سرویس | خطای **موقت** با ذکر کد |

متدهایی که با کاوش زنده **تأیید** شدند:

| متد | کاربرد | شکل `data` در پاسخ مشاهده‌شده |
|---|---|---|
| `send` | ارسال پیام | آرایه؛ در خطا `[{"ErrorCode":"E5"}]` |
| `getbalance` | اعتبار حساب (ریال) | رشته؛ در خطا `"E5"`، در موفقیت رشته عددی |

متدهایی که کاوش شدند و **وجود ندارند** (همه `code:111` دادند): `balance`, `credit`, `getCredit`,
`getBalance`, `status`, `getstatus`, `getstatuses`, `getstatuses_originalid`, `getstatus_originalid`,
`delivery`, `getdelivery`, `getdlr`, `statusbyid`, `getstatusbyid`, `report`, `getreport`,
`receive`, `viewreceive`, `acknowledge`, `sendmultiple`.

> **نتیجه مهم:** درگاه REST این سرویس‌دهنده متدِ **وضعیت تحویل** ندارد. بنابراین در حالت `Api`،
> `GetDeliveryStatusAsync` بدون هیچ فراخوان شبکه، صادقانه `Unknown` برمی‌گرداند و پیام
> پذیرفته‌شده همان‌طور می‌ماند (نه تحویل‌شده و نه ناموفق). اگر روزی سرویس‌دهنده متد وضعیت
> اضافه کرد، این بخش به‌روزرسانی می‌شود.

### کدهای خطای داخل `data`

کدهای خطا همان جدول ۲۱ کد سند SOAP هستند (`E5` احراز هویت، `E6` کمبود اعتبار، `E43` شماره
نامعتبر، …). پیاده‌سازی همان `PayamSmsFaults` حالت Wsdl را دوباره استفاده می‌کند تا
دائم/موقت بودن خطاها یکسان بماند. نمونه مشاهده‌شده با اعتبار نامعتبر:

```json
{ "code": 200, "message": "send result", "data": [ { "ErrorCode": "E5" } ] }
```

## ۳. شکل پاسخ موفق `send` (استنباطی — هنوز با پاسخ زنده تأیید نشده)

چون کاوش زنده با اعتبار نامعتبر انجام شد، پاسخ موفقِ `send` دیده نشد. شکل موفق از قرارداد
SOAP وام گرفته شده است: آرایه‌ای از `{ID, Mobile}` که `ID` شناسه یکتای پیام است.

```json
{ "code": 200, "message": "send result", "data": [ { "ID": "700123", "Mobile": "989121112233" } ] }
```

پیاده‌سازی محافظه‌کار است: **تا وقتی یک `ID` غیرخالی و غیرکدخطا برنگردد، هیچ پاسخی «موفق»
ثبت نمی‌شود.** هر پاسخ مبهم (آرایه خالی، شیء بدون `ID`، `data` غایب) «موقت/تلاش مجدد» می‌ماند.
اگر شکل واقعی پاسخ موفق با این استنباط فرق داشت، فقط `MapSendData` باید اصلاح شود.

## ۴. وضعیت پیاده‌سازی در این مخزن

| موضوع | قرارداد REST | کد این مخزن |
|---|---|---|
| آدرس | `…/services/rest/index.php` | `sms.endpoint`؛ اگر خالی باشد `DefaultEndpoint` |
| احراز هویت | organization/username/password در بدنه | همان کلیدهای حالت Wsdl؛ رمز از انبار اسرار (`GetSecretAsync`) |
| ارسال | `method:"send"` + `messages[]` | یک گیرنده در هر فراخوانی (صف گیرنده‌به‌گیرنده) |
| `customerId` | ثابت `1` در پروسیجر مرجع | `CustomerId = 1` |
| اعتبار | `method:"getbalance"` | `GetBalanceAsync`؛ رشته یا عدد → `RawCredit` |
| وضعیت تحویل | متد ندارد | `Unknown` بدون فراخوان شبکه |
| کدهای خطا | همان Eهای سند SOAP | `PayamSmsFaults` مشترک |
| نرمال‌سازی شماره | کد کشور + حداکثر ۱۲ رقم | `PayamSmsGateway.NormalizeDestination` مشترک |
| کدگذاری بدنه | UTF-8 خام (مطابق پروسیجر) | `JavaScriptEncoder.UnsafeRelaxedJsonEscaping` |

سه نکته:
۱) همه تنظیمات از پایگاه داده خوانده می‌شوند و تغییر حالت/آدرس/رمز نیاز به restart ندارد.
۲) `code:111` دائمی است چون یک خطای پیکربندی است، نه خطای گذرا؛ صف آن را بی‌پایان تکرار نمی‌کند.
۳) متن خام خطای سرویس‌دهنده فقط در لاگ می‌نشیند؛ پیام کاربر فارسی و عمومی است.

## ۵. راه‌اندازی برای مدیر

۱. در تب «اتصال سرویس‌ها» روش ارسال را `Api` بگذارید.
۲. آدرس سرویس `https://www.payamsms.com/services/rest/index.php` (پیش‌فرض اگر خالی بماند).
۳. سازمان، شناسه کاربری، شماره فرستنده و **رمز جاری** پنل را وارد کنید.
۴. «تست اعتبار درگاه» باید اعتبار واقعی (ریال) را برگرداند. اگر `E5` دیدید، شناسه/رمز اشتباه است.

> هشدار: اعتبارنامه‌ها هرگز در مخزن ذخیره نمی‌شوند؛ رمز فقط رمزنگاری‌شده در پایگاه داده می‌نشیند.

آزمون‌ها: [tests/NovaFleet.UnitTests/Sms/PayamSmsRestGatewayTests.cs](../../tests/NovaFleet.UnitTests/Sms/PayamSmsRestGatewayTests.cs)
با `HttpMessageHandler` ساختگی، شکل JSON، نرمال‌سازی گیرنده، کدگذاری UTF-8، طبقه‌بندی خطاها،
`getbalance` و انتخاب حالت `Api` از دیتابیس را می‌سنجند.
